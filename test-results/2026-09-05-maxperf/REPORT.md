# 측정 — 최대 성능 재측정 (1 GbE 링크, 2026-09-05)

- **리포**: `dev` = `95740c5`, 버전 `1.3.0`, 배포 바이너리 `v1.0.9-27-g6df0c8b-dirty`
- **선행**: [온링크 전환 후 계단 (2026-08-06)](../2026-08-06-postmove-loadtest/REPORT.md) — 같은 계단을 **100 Mbps 링크**에서 · [c 복구 후 재검증 (08-31~09-02)](../2026-08-31-postfix-recheck/REPORT.md) — 지속 18 통과
- **동기**: `c` 의 링크가 08-31 현장 조치로 **100 → 1000 Mbps** 가 됐다. 08-06 계단의 붕괴점(각 34 Mbps)에서 c 회선이 약 180 Mbps(RX+TX) = **당시 링크 방향당 90%** 였으므로, 그 붕괴가 CPU 가 아니라 링크 포화였을 가능성이 있었다.

## 2. 지속 소크 (`mf_soak_18m.sh`, 운영 체인 :443)

### 2-가. 각 24 Mbps — 2분 57초에 붕괴 ❌

가드 트립(1코어 90.6% · 전체 72.0%)이 **손실 폭발 직후**에 왔다. 클라 집계는 SIGKILL 로 유실됐고 `s` 수신 로그로 초 단위 복원했다.

| 구간 | 실효 | c→s 손실 |
|---|---|---|
| 0–30초 | 23.94 | 0.048% |
| 30–150초 | 24.00 | 0.008 ~ 0.021% |
| **150–180초** | 23.75 | **0.948%** |

**150초까지 완벽했다.** 169초에 351개(그 초의 **15.1%**), 170초에 148개(5.8%)가 한꺼번에 사라졌다 — 전체 136초 중 손실이 난 35초 가운데 499개가 이 2초에 몰렸다. 회선은 1 GbE 의 12.9% 뿐이라 링크와 무관하다.

**45초 계단에서 24 가 통과한 이유는 창이 이 사건 전에 끝나기 때문이다.**

### 2-나. 각 22 Mbps — 손실 0 인데 코어가 포화 ⚠️

3회 시도 전부 19~24초에 트립. **손실은 0**(±1~2 는 재정렬 아티팩트)이었다.

결정적 증거는 `c` 자신의 로컬 샘플러(ssh 비용 없음)다:

```
multi-fec 프로세스 CPU = 83.5%   (단일 스레드 → 코어 하나의 83.5%)
가드 최고1코어         = 88.9 ~ 91.8%   (= 프로세스 + 수신 softirq + 가드 오버헤드 4.7p)
```

가드 오버헤드를 빼도 **84~87%**. 손실은 아직 없지만 **여유가 없다** — 24 에서 터진 것이 이 여유 없음이다.

### 2-다. 각 20 Mbps — 1시간 완주 ✅ (새 지속 상한)

두 번 돌렸다. 첫 런(기본 임계)은 **32분 무열화 후** 1코어 87.5% 로 트립했고, `GW_CORE=90` 으로 다시 돌려 완주했다(§3-나).

| | 값 |
|---|---|
| c→s | **109 / 7,211,538 = 0.0015%** |
| s→c | **136 / 7,211,540 = 0.0019%** |
| 실효 | 양방향 **20.0 Mbps** — 60개 구간 전부 |
| 회선 | 107.5 Mbps (RX 53.7 + TX 53.8) = **증폭 2.69배** |

**손실이 시간에 따라 커지지 않는다** (10분 단위, s→c):

```
0.0067% → 0.0008% → 0.0003% → 0.0033% → 0.00008% → 0.00008%
                                          ↑ 마지막 20분은 10분에 1패킷
```

**자원 — 누수 0, 드리프트 없음**

| | RSS | 변화 | FD | CPU 6구간 |
|---|---|---|---|---|
| c 클라이언트 | 15.01 → **15.01 MB** | **0회** | 8 고정 | 75.6 → 78.8 → 79.9 → 79.3 → 77.9 → **78.4** (Δ+2.8p) |
| r 릴레이×2 | 1.36 → 1.36 MB | 0회 | 14 고정 | 51.0 → … → 52.0 (Δ+1.0p) |
| s 서버 | 37.14 → 37.14 MB | 0회 | 8 고정 | 32.4 → … → 32.9 (Δ+0.5p) |

**RSS 가 1시간 동안 1 KB 도 변하지 않았다**(세 호스트 전부). CPU 는 1구간 워밍업 뒤 평탄하고 후반에 내려간다.

첫 런(임계 85, 32분)도 같은 성질이었다 — 손실 5분 구간 0.0115~0.0145% **완전 평탄**, CPU 73→80→77.9% (하락), RSS 15.01 MB 변화 0회.

## 3. 가드 계측 — 도구가 피측정계를 흔든다

### 3-가. ssh 오버헤드와 ControlMaster (적용 완료)

가드는 샘플마다 원격에 ssh 를 새로 맺는다. Atom N2600 에서는 sshd + 키교환이 코어를 크게 흔든다. **트래픽 0 인 상태로 A/B** (인스턴스 수를 `ps` 로 검증하고 측정):

| c 상태 | 전체 busy | cpu0 | cpu1 | cpu2 | cpu3 |
|---|---|---|---|---|---|
| 가드 없음 | **0.5~0.7%** | 0.2 | 0.2 | 0.5 | 1.1 |
| 가드 (수정 전) | **11.5%** | 17.0 | 9.4 | 11.2 | 8.9 |
| **가드 (ControlMaster)** | **4.2%** | 4.5 | 3.6 | 4.7 | 4.3 |

**수정**: `mf_gwguard.sh` 의 ssh 호출 5곳을 래퍼로 교체. **임계값·판정 로직 무변경.**

```bash
SSH() { command ssh -o ConnectTimeout=5 \
        -o ControlMaster=auto -o "ControlPath=$GW_CM_DIR/%r@%h:%p" -o ControlPersist=120 "$@"; }
```

백업은 로컬 `mf_gwguard.sh.bak-precontrolmaster` 와 git 이력. 오버헤드 **11.5% → 4.2%**(코어당 8~17p → 3.6~4.7p).

### 3-나. 1코어 임계 85% 는 이 레이트에서 오탐한다

20 Mbps 첫 런은 **32분간 손실·CPU·메모리 어느 것도 나빠지지 않았는데** 1코어 87.5% 로 트립했다. 그 32분 동안 단발 초과가 **107건**이었고 연속 3회가 우연히 겹친 순간 잘렸다.

`GW_CORE=90` 으로 올리자 **초과가 8건으로 줄고 1시간을 완주**했다. 그 8건도 대부분 `c` 가 아니라 `r` 이었다:

```
15:23  r 1코어 94.9 / 95.0 / 97.0%      ← r 프로세스 CPU 는 52% 평탄. VM 호스트 부하 또는 샘플 창
15:53  r 1코어 100.0 / 99.0%
15:32  c 전체 62.4% (임계 62)            ← 단 1회, 경계 스침
16:10  c 1코어 93.2%                     ← 종료 직전
```

**85 의 근거가 흔들렸다.** 그 값은 08-06 계단(3회 평균)으로 정했는데, 위 §1 경고대로 계단은 CPU 를 과소평가한다. 정상 구간인 c 1코어 78~80% 에 임계가 붙어 있어 오탐한다.

> **재보정은 하지 않았다** — 90 은 08-06 에 34 Mbps 붕괴(1코어 85.7%)를 놓친 값이다. 이번 런은 `GW_CORE=90` 을 **그 런에 한해** 넘겨 돌렸고, 백스톱으로 c 전체 62%·손실 초 단위 관측·실효 이탈을 두었다. 항구적 임계 변경은 별도 판단이 필요하다.

## 4. 절차 실패 기록 (측정자 과실)

### 4-가. 34 단계가 가드 없이 돌았다

30 에서 가드가 트립해 종료했는데 하네스의 생존 검사 `pgrep -f '[m]f_gwguard.sh watch'` 가 **종료 중이던 프로세스를 매치**해 34 를 그대로 진행했다. 피해는 없었다(45초 만에 종료, c 58.7%, 회선 1 GbE 의 18%, 잔여 부하 0). **조치 필요**: 생존 검사를 **가드 PID 보관 후 `kill -0`** 으로 바꿀 것. 측정 중 하네스를 바꾸면 앞뒤 단계가 비교 불가라 이번 런에서는 고치지 않았다.

### 4-나. `pkill -f` 가 자기 셸을 죽여 가드가 누적됐다 — 하루에 3회

`pkill -f "mf_gwguard.sh watch"` 는 **패턴이 자기 명령줄에 평문으로 들어가** 호출 셸을 먼저 죽인다(exit 144). 그 결과 가드가 살아남아 누적됐고, 22 Mbps 트립 2건에 오염이 섞여 재현 확인에 런 2회를 더 썼다. **리포에 이미 기록된 함정**(하네스 함정 #4 계열)인데 오늘 세 번 반복했다.

**교훈**: 정리는 `ps -eo pid,args` 로 목록을 만든 뒤 **PID 로 kill** 한다. 문자열 매치를 쓰지 않는다.

### 4-다. 인스턴스 개수를 mux 소켓까지 세었다

`ps | grep mf_gwguard` 가 ControlMaster mux(`ssh: /tmp/mf_gwguard_cm/...`)까지 매치해 "가드 5개" 로 보였다. 실제 가드 루프는 그보다 적었다. 세는 패턴은 `mf_gwguard(\.sh)? (watch|sample)` 로 좁혀야 한다.
