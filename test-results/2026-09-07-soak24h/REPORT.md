## 1. 구성

```
지사 i (i=0..9):  [mf_blast] 10.9.(20+i).2 ──wg mft{i}── 10.9.(20+i).1 [rt_echo_ip]
                       │
                  multi-fec client{i} ─┬─▶ r .85:4443 ─┐
                                       └─▶ r .86:4443 ─┴─▶ multi-fec server{i} (.84:4500+i)
                                           (--route 로 키별 분기, 릴레이 2개)
```

운영 무침습: WG `mft0..9`(운영 `starlink-fec`) · 서브넷 `10.9.20~29`(운영 `10.9.9/10.9.10`) · 클라 `:51900~`(운영 `:51821`) · 서버 `:4500~` · 릴레이 `:4443`(운영 `:443`).

설정은 duplicate · `--mode 1` · `-f 5:1,20:4` · `--fec-timeout 10` · `--mtu 1350` · netem path[0] 25ms/5% · path[1] 30ms/2%. 가드는 **`GW_STREAK=5`**(이유는 §4).

**하네스**: `mf_wg_soak24h.sh` — 2026-09-02 판을 **청크화**했다. `mf_blast` 는 종료 시에만 집계를 뱉으므로 24시간을 한 번에 돌리면 중간에 죽을 때 전부 잃는다(2026-09-05 24 Mbps 런에서 실제로 겪었다). 세션·WG·프로세스는 청크 사이에 유지된다.

## 2. 1차 런 — 17시간, `s` 의 apt 가 끊었다

첫 시도는 **17시간에서 가드 트립**으로 끝났다. 원인은 우리 부하가 아니다:

06:36:42  s: systemd[1]: Starting Daily apt upgrade and clean activities...
06:36:45  가드: s:1코어=100.0%>90%  (1/5)
06:36:46~49                100.0 · 100.0 · 100.0

## 3. 2차 런 — 24시간 완주

### 3-가. 전달

```
청크별 유실 (각 1시간, 청크당 3,750,000 왕복):
22 14 12 19 16 16 | 13 13  8 12 18 14 | 20  8 17 15 | 12 13  9 13 20 11 16  9

누적  89,713,550 중 340  =  0.000379%   (회수율 99.999621%)
오배송 0 · 불량 0 · pacing_resets=0 · sendfail=0
```

**4분위 평균 유실 16.5 · 13.0 · 14.2 · 13.0 — 시간이 갈수록 나빠지지 않는다.** 마지막 청크(9)가 최저 그룹에 든다.

### 3-나. 자원 — 누수 없음

| | RSS | 계단 | **마지막 변화 이후** | FD | CPU 8구간 |
|---|---|---|---|---|---|
| c (10proc) | 111.54 → 131.04 MB | 30회 | **23.6시간 불변** | 70 | 126.7 → 123.3 (**Δ−3.4**) |
| r (2proc) | 3.16 → **3.16 MB** | **0회** | **24.0시간 불변** | 32 | 41.5 → 41.2 (Δ−0.3) |
| s (10proc) | 111.34 → 130.22 MB | 33회 | **23.3시간 불변** | 70 | 44.5 → 44.1 (Δ−0.4) |

계단은 **c 는 24분 · s 는 43분** 에 끝났고 그 뒤로 1 KB 도 움직이지 않았다. `r` 은 24시간 동안 **변화가 아예 0회**다. **CPU 는 세 호스트 모두 내려갔다.**

> c 의 Δ−3.4 중 상당 부분은 6시간 지점에 정리한 잔존 샘플러 효과다(§5-가). 그 이후 구간만 보면 123.7 → 123.3 으로 평탄하다.

### 3-다. 회선 — 사이징 식의 24시간 교차검증

| 계층 | 실측 |
|---|---|
| 앱 페이로드 | 10세션 × 각 방향 1 Mbps = **양방향 20 Mbps** |
| WG 터널 통과량 | 터널당 2.10 Mbps × 10 = **21.0 Mbps** |
| **c `enp2s0`** | RX 35.22 + TX 37.42 = **72.64 Mbps** |
| r `ens18` | RX 73.70 + TX 72.40 = 146.10 Mbps (릴레이가 2경로를 나른다) |
| s `ens18` | RX 37.31 + TX 36.37 = 73.68 Mbps |

**증폭 3.63배.** [사이징 식](../2026-09-04-sizing/REPORT.md) 이 R=1·N=10 에 예측한 **71.0 Mbps** 와 **+2.3%** 로 일치한다 — 1시간 런에서 세운 식이 24시간에서도 유지된다.

## 4. 가드 — 트립 0, 그러나 임계는 이 구조에 낮다

```
초과 2,400건 · 트립 0 · 최대 연속 3 (트립 필요 5)

지표별:  c:전체 2,329건 (max 93.4%) · c:1코어 291건 (max 100.0%)
         r:1코어    45건 (max 100.0%) · r:링크 1건 (max 499.73 Mbps)
```

**`GW_STREAK=5` 가 24시간을 살렸다.** 최대 연속이 3까지 갔으므로 **기본값 `STREAK=3` 이면 또 트립했을 것**이다.

⚠️ **가드 임계는 부하 구조별로 달라야 한다.** 어제 재보정한 `c 전체 68` 은 **단일 세션 기준**이다:

| 구조 | c 전체 CPU |
|---|---|
| 단일 세션 각 20 Mbps (2026-09-05) | max **53.9%** |
| **10지사 × 각 1 Mbps** | 상시 **68~93%** (초과 2,329건) |

10세션은 프로세스 10개 합 123% + WG 암복호 10개가 얹혀 머신 부하 자체가 다르다. **손실·RSS·FD·CPU 가 모두 평탄하므로 이 2,329건은 전부 오탐이다.**

### `r:링크 499.73 Mbps` 는 증폭 루프가 아니다

링크 임계는 2026-08-03 의 800 Mbps 사고류를 잡는 백스톱이라 반드시 확인해야 한다. 05:53:27 의 그 1건은 **§5-나 의 인프라 버스트**다:

```
05:53:19  r 머신 10.9%  릴레이 프로세스 40.0%
05:53:29  r 머신 39.6%  릴레이 프로세스 44.2%   ← 릴레이는 거의 안 움직였다
05:53:50  r 머신 11.1%  릴레이 프로세스 42.5%
```

`:53` 주기와 정확히 일치하고 릴레이 CPU 는 평탄하다 — 컨테이너의 네트워크 동기화이며 **같은 원인이 CPU 와 링크 두 지표에 나타났다.**

## 5. 이번에 잡은 결함·관측

### 5-가. 하네스 결함 — 샘플러 CSV 경로가 런 간에 충돌한다 ★

온호스트 경로가 `/tmp/wg_{c,r,s}.csv` 로 **고정**이고 샘플러 수명이 `SECS+600`(24.2시간)이다. 1차가 17시간에 트립으로 끝났어도 **샘플러는 계속 돌았고**, 2차 샘플러와 같은 파일에 동시 기록했다:

```
1788839034,10,134188,70,126.4,52.9    ← 2차
1788839034,10,134188,70,126.6,53.1    ← 1차 잔존 (같은 초, 중복 행)
```

값은 서로 일치해 분석 방향은 틀리지 않았지만 행이 2배로 늘어 시계열이 오염된다. **PID 로 종료**해 해소했다(c·r 각 1개, s 는 트립 시 정리돼 없었다).

**부수 발견**: 잔존 샘플러 하나(10초 주기 bash)가 **가드 초과를 14배로 만들었다** — 6시간까지 2,000건 → 정리 후 6시간당 124~144건. `c` 전체가 임계 68 바로 위에 걸려 있어 **계측 부하 하나가 그 차이를 만든다.** 임계 근처 운용에서는 계측 도구의 부하를 반드시 세야 한다.

→ **조치 완료 (2026-09-09)**: 하네스 7개에 `RUNID` 를 도입했다.

```bash
RUNID=${RUNID:-$(basename "${OUT:-run}")-$(date +%m%d%H%M%S)}
# → /tmp/wg_c_wg_raw-0909091702.csv  처럼 런마다 유일
```

대상: `mf_wg_soak24h.sh` · `mf_wg_multi.sh` · `mf_amp_ladder.sh` · `mf_soak_18m.sh` ·
`mf_aging_1h.sh` · `mf_multi_soak.sh` · `mf_rt_multi.sh`(샘플러 시작만 — 이 옛 하네스는
스크립트 내에서 회수하지 않는다). 회수 라인은 단일따옴표에서는 변수가 확장되지 않으므로
쌍따옴표로 바꿨다. 스모크(10세션 × 120초)로 기록·회수를 확인하고 호스트에 남아 있던
옛 고정경로 파일(최대 345 KB)을 정리했다.

### 5-나. `r` 의 1코어 스파이크 = 인프라 컨테이너 (별도 규명)

`r` 의 30분 주기(`:23`/`:53`) 버스트는 [2026-09-05 REPORT §3-마](../2026-09-05-maxperf/REPORT.md) 에서 규명했다 — `infra-collector`/`infra-pb` 다. 이번 24시간 런에서 **CPU 45건 + 링크 1건**으로 다시 확인됐다.

### 5-다. 청크 카운트 off-by-one (수정 완료)

스모크에서 "3개 완료" 인데 실제 2개였다 — `k` 를 `break` 전에 올렸다. 실제로 돈 청크만 세도록 고쳤다.

### 5-라. `s` 는 공인 노출로 상시 공격받는다

`s` 저널에 **하루 1,908건의 SSH 무차별 대입**(36.255.97.9 등)과 `ens20` 의 `dhclient` DHCPDISCOVER 무한 반복이 있다. 1차 트립의 주원인은 아니었지만(트립 분 인증 실패 3건) **장시간 측정의 배경 잡음원**이다.

## 8. 후속 — 가드 프로파일 분리 (2026-09-09, 적용 완료)

이 런이 만든 초과 2,329건(전부 오탐)이 근거다. **수준이 아니라 지속성으로 가른다** — 24시간 **정상** 런의 초과 샘플을 후보 임계에 재생해 최대 연속을 구했다:

| 지표 | 분포 | 최대 연속 |
|---|---|---|
| c 전체 | p50 77.1 · p90 87.3 · max 93.4 | 임계 68 → **3** · **75 이상 → 1** |
| c 1코어 | p50 91.5 · max 100.0 | 90~95 → **3** · 98 → 1 |
| r 1코어 | max 100.0 (인프라 버스트) | 95 → **3** |

```
GW_PROFILE=single (기본)   c 전체 68 · 1코어 90 · streak 3    ← 2026-09-05 재보정
GW_PROFILE=multi           c 전체 78 · 1코어 95 · streak 5    ← 이 런에서 도출
r·s 전체 75 · 링크 400 Mbps — 공통
```

정상 런의 최대 연속(1·3)에 2배 이상 여유가 있고, 진짜 과부하는 수십 초~분 단위라 그대로 잡힌다. `s` 의 apt(95 이상 4초)와 `r` 의 인프라 버스트(3초)는 통과시킨다 — **둘 다 우리 부하가 아니다.**

⚠️ **`multi` 를 단일 세션에 쓰면 안 된다** — 24M 붕괴를 아예 못 잡는다(연속 0). 다중 세션 하네스(`mf_wg_soak24h.sh` · `mf_wg_multi.sh`)에 `GW_PROFILE=multi` 를 고정했다.

⚠️ **재생 방법을 바로잡는 과정에서 09-05 보고서의 오류를 찾았다** — [2026-09-05 §3-다](/doc/2dzkYWEBUd) 참고. 연속성은 벽시계 간격이나 단순 건수가 아니라 가드의 `초과(N/M)` 카운터로 판정해야 하고, 트립 줄도 샘플로 세야 한다.
