| 누수 | 0 | 0 | 0 | **0** | 0 |

### 이 문서의 이전 판(09-02 오전)에서 두 가지를 취소한다

**① "지속 한계 `16 < X < 18`" — 틀렸다.** 18 이 통과했으므로 한계는 **18 보다 위**이고,
현재 구성에서는 미측정이다.

**② "CPU 드리프트가 부하에 단조증가한다" — 틀렸다.** 18 에서 **+0.6p** 가 나와
12(+0.3) → 14(+1.5) → 16(+3.6) → 18(+0.6) 으로 단조가 깨진다. 애초에 그 계열은 출처와 런
길이가 섞여 있었다(12 는 08-07 의 1시간 값, 나머지는 오늘). **드리프트는 부하의 함수가 아니라
런마다 흔들리는 값**으로 보는 것이 맞다 — 30분 평균의 차인데 원신호가 40~58% 로 요동한다.

### 08-07 은 왜 무너졌나 — 미규명

같은 바이너리(v1.0.9), 같은 설정, 같은 netem 으로 재현되지 않는다. 확인된 차이는
**c 의 링크가 그 사이 100 → 1000 Mbps 로 바뀐 것**뿐인데, 이것이 원인이라 단정할 수 없다:

- 18 Mbps 에서 c `enp2s0` 은 **RX 48.79 / TX 48.70 Mbps** 다. 100 Mbps **전이중**이면
  방향당 49% 라 포화가 아니다 → 속도만으로는 설명되지 않는다
- 다만 2026-08-24 부팅 로그에 `Link Speed was downgraded by SmartSpeed` 가 있다. 링크
  오류로 재훈련이 일어났다는 신호라 **케이블·포트가 marginal 했을 가능성**을 시사하고,
  08-31 13:44 현장 조치 후 1000 Mbps 로 올라온 것과 정합적이다
- **그러나 08-07 시점의 링크 속도·오류 카운터는 저널에 남아 있지 않아 확인 불가다**
  (05-18 부팅의 `NIC Link is Up` 기록이 로테이션으로 사라졌다)

`c` 의 시계 드리프트(chrony 미기동)가 언제 시작됐는지도 확정할 수 없다. 08-07 에 이미
진행 중이었다면 영향이 있었을 수 있으나 **근거가 없다.**

**결론: 08-07 의 붕괴는 재현되지 않으며 원인은 미규명이다. 그 값을 한계의 근거로 쓸 수 없다.**

### 운용 권고

**검증된 지속 상한은 각 방향 18 Mbps 다.** 다만 SLA 로는 **14~16** 을 권한다 — 16·18 에서
`c` 가 가드 임계에 순간적으로 닿기 시작하고(§3-다·§4-다), 실서비스는 netem 보다 변동이 큰
실경로를 탄다. 상한 자체를 SLA 로 쓰면 여유가 없다.

## 1. 배경 — 12일간의 측정 공백과 그 원인

2026-08-19 09:43 부터 08-31 15:04 까지 테스트망 터널이 죽어 있었다. 기존 기록은
"c 전원/NIC 다운, 현장 조치 필요" 였는데 **절반만 맞았다.**

```
부팅 시 enabled 유닛 24개가 오류 한 줄 없이 미기동
  └ 그중 chrony 포함  →  NTP 미동작  →  시계 +73.9초 드리프트
      └ mud timetolerance = 30초  →  서버가 전 패킷 무음 폐기
          └ 경로 DEGRADED rx=0  →  터널 정지
```

링크는 실제로 끊겨 있었고 08-31 13:44 에 현장 조치로 복귀했지만(100 → **1000 Mbps**),
그것만으로는 터널이 살아나지 않았다. **시계가 남은 원인이었다.**

> **진단이 어려운 이유**: 릴레이 로그에는 `new session` 이 정상적으로 찍힌다. HMAC 슬롯은
> `--auth-interval 60` 에 ±1 슬롯 허용이라 74초 오차를 통과하는데, **mud timetolerance 30초는
> 통과하지 못한다.** 두 관문의 허용치가 달라 "인증은 되는데 데이터만 안 가는" 모습이 된다.

부팅 미기동의 원인은 로그에 근거가 없어 규명하지 못했다(ordering cycle·dependency failed·
job deleted 전무). 원인에 기대지 않는 자가 복구 `mf-chain-ensure` 를 c 에 설치했다 — §7.

## 7. 부수 조치 — `mf-chain-ensure` (c)

부팅 미기동의 원인을 규명하지 못했으므로 **원인에 기대지 않는 자가 복구**를 넣었다.
2분 주기 systemd timer.

| 파일 | 역할 |
|---|---|
| `/usr/local/sbin/mf-chain-ensure.sh` | 본체 |
| `/etc/systemd/system/mf-chain-ensure.{service,timer}` | enabled |
| `…/systemd-networkd-wait-online.service.d/10-iface.conf` | `--interface=enp2s0` 한정 |

- 시계 오차 > 5초 → `chronyc makestep`, chrony 정지 시 기동
- netem qdisc < 2개 → `mf-netem` 재적용 (링크 플랩이 qdisc 를 지운다)
- 체인 유닛 정지 시 순서대로 기동

**원칙: 멈춘 것만 기동한다. 돌고 있는 유닛은 절대 재시작하지 않는다.** 네 가지 동작을 실측
검증했고, **네 번의 1시간 소크 동안 간섭이 없었음**을 확인했다.

> ⚠️ 측정 중 완전히 손 떼게 하려면 `touch /run/multi-fec/no-autoheal`.

## 10. 하네스 교훈 (신규 3건)

**① 완료 대기 루프가 자기 자신을 매치해 영원히 안 끝난다.** 12 런은 08-31 15:23 에 정상
종료했는데 후속 14 런이 이틀 뒤에야 시작됐다.

```bash
# ✗ 이 루프의 셸 커맨드라인에 패턴이 들어 있어 스스로를 매치 → 무한 대기
until ! pgrep -f "mf_soak_18m.sh" >/dev/null; do sleep 10; done

# ✓ PID 로 기다린다 — 문자열 매치를 아예 쓰지 않는다
setsid bash -c "echo \$\$ > run.pid; exec env RATE=18 ./mf_soak_18m.sh" > run.log 2>&1 &
P=$(cat run.pid); while kill -0 "$P" 2>/dev/null; do sleep 20; done
```

bracket 우회도 못 쓴다 — `until` 루프 전체가 한 줄로 `bash -c` 에 들어가므로 패턴 평문이
뒤쪽에 그대로 남는다. `setsid ... & echo $!` 도 못 쓴다(즉시 종료하는 래퍼의 pid).

**② c→s 방향의 구간별 손실은 클라이언트 로그에 없다.** iperf3 `--bidir` 에서 송신측 구간
줄에는 손실 칼럼이 없고 최종 요약에만 있다. 구간 분석에는 **수신측 `s` 의
`/tmp/sk_srv.log`**(1초 해상도)가 필요하다. §5 의 "단일 사건" 판정이 이 로그로만 가능했다.

**③ 1초 구간 손실을 그냥 더하면 안 된다.** 재정렬 때문에 음수 손실 구간이 생기고,
`max(loss,0)` 으로 합하면 실제 0 인 손실이 수백 개로 부풀어 보인다. **부호를 살려 합산**해야
순손실이 나온다.
