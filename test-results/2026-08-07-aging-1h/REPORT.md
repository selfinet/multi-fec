# 측정 — 지속 부하 소크: 45초 계단 값은 지속되지 않는다 (2026-08-07)

원본: `test-results/2026-08-07-aging-1h/` · 테스트망 c·r·s · 전 호스트 v1.3.0(배포본 v1.0.9)

---

## 0. 요약

| 항목 | 결과 |
|---|---|
| **핵심 결론** | **45초 계단이 준 "실용 한계 각 방향 22 Mbps" 는 지속 부하에서 성립하지 않는다** |
| 각 방향 18 Mbps | **21분 12초에 붕괴** — 손실이 전반 0.051% → 후반 0.218% 로 커지고 가드 트립 |
| 각 방향 12 Mbps | **1시간 완주** — c→s 순손실 **0**, s→c 0.0017%, CPU 평탄, 누수 0 |
| **지속 운용점 (확정)** | **각 방향 12 Mbps** (양방향 24, 회선 66 Mbps) |
| 지속 한계 | **12 < X < 18** — 미측정 |
| 메모리·FD 누수 | **없음.** 저부하 8세션 48분 · 고부하 1시간 양쪽에서 마지막 30분 기울기 +0.00 MB/시간 |
| 트래픽 격납 | **전량 테스트망 안.** 3개 런 전부 외부 인터페이스 ±0.000 Mbps |
| 하네스 결함 | **4건 발견·수정** (§7). 그중 하나는 운영 클라이언트를 20분 죽였다 |

**결론**: 처리량 상한을 "얼마나 빨리 갈 수 있나" 로 재면 안 된다. 18 Mbps 는 실효
17.98 Mbps 를 **끝까지 유지**했다 — 무너진 것은 처리량이 아니라 손실이다. 45초 창은 그
열화가 나타나기 전에 끝난다.

---

## 1. 배경 — 왜 했나

2026-08-06 계단 시험(`../2026-08-06-postmove-loadtest/REPORT.md` §9)이 "실용 한계 각 방향
22 Mbps" 를 냈다. 그 값은 **단계당 45초**다. SLA 로 쓰려면 지속 부하에서 유지되는지 확인이
필요했다. 아울러 고부하에서의 메모리 누수는 한 번도 본 적이 없었다 — 기존 소크는 전부
저레이트였다.

---

## 2. 구성

계단과 **동일 조건**으로 맞췄다. 비교 가능해야 의미가 있다.

```
c 192.168.100.141 ──┬─ path[0] → r 192.168.100.85:443 ─┐
                    └─ path[1] → r 192.168.100.86:443 ─┴→ s 192.168.100.84:443
                       (netem 25ms/5%)   (netem 30ms/2%)      임피어먼트 없음
```

| | 설정 |
|---|---|
| multi-fec | 운영 체인(:443) · `duplicate` · `--mode 1` · `-f 5:1,20:4` · `--fec-timeout 10` · `--mtu 1350` |
| 부하 | `iperf3 -u --bidir`, WG IP 사이 (`-B 10.9.10.1`) — 규칙 1 |
| 가드 | `mf_gwguard.sh watch "iperf3 -c"`, 부하보다 **먼저** 기동 (규칙 0) |

**UDP 를 쓴 이유**: 고정 레이트라 손실이 그대로 보인다. TCP 는 스스로 레이트를 낮춰 "어디서
무너지는가" 를 흐린다. 또 iperf 3.9 의 TCP `--bidir` 에는 36배 붕괴하는 도구 결함이 있다.

## 3. 저부하 에이징 — 8세션 × 각 방향 0.25 Mbps (48분)

병렬 체인(:4443)으로 운영 무침습. `blaster_i → client_i → relay×2 → server → echo → 역방향`
왕복이라 하향까지 검증한다.

### 3-가. 누수 없음

판정은 **마지막 30분 기울기**로 한다. 전반의 양수 기울기는 페이지를 처음 만지며 오르는
램프이고, 그것과 누수를 구분하는 것이 요점이다.

| | c (클라 8 + 운영 1) | r (릴레이 2 + 운영 2) | s (서버 1, 8연결) |
|---|---|---|---|
| RSS 수렴 | **115.2 MB** | **4.2 MB** | **88.9 MB** |
| 전반 기울기 | +29.74 MB/h | +0.07 | +47.52 |
| **마지막 30분** | **+0.00 MB/h** | **+0.00** | **+0.33** |
| FD (마지막 30분) | 64 고정 | 42 고정 | 14 고정 |

램프는 약 20분에 끝나고 이후 완전히 평탄하다(종료 직전 6샘플이 소수점까지 고정).
s 연결당 메모리 88.9÷8 = **11.1 MB** — 예측 9.4, 2026-08-03 검증 10.55 와 같은 범위.

### 3-나. 전달 99.997%

가드가 집계 프로세스를 SIGKILL 해 태그 집계(`result.csv`)가 유실됐다. 클라이언트 report
로그에서 복구했다.

```
상향 original 594,616 pkt → 하향 original 594,601 pkt = 99.997%
세션별 99.995~99.999%   FEC 증폭 2.02×
```

미도달 15패킷은 강제 종료 시점의 인플라이트다.

> ⚠️ **오배송 직접 검증은 못 했다.** 태그 기반 own/foreign 집계가 유실됐다. 8세션이 전부
> 99.995% 이상이라 정황상 0 이지만(오배송이 있었다면 해당 세션 하향이 깎였을 것) 직접
> 증거는 아니다.

### 3-다. 조기 종료 원인은 부하가 아니었다

r 의 릴레이 프로세스 CPU 는 트립 순간까지 13.5→14.5% 로 **평탄**한데 시스템 전체 busy 만
8.8→37.1% 로 튀었다. r 저널(**UTC** — r 만 UTC)이 특정한다:

```
Aug 07 02:57:21  Starting Daily apt download activities...
Aug 07 02:57:54  apt-daily.service: Consumed 27.268s CPU time
```

**11:57:21~11:57:54 KST 의 `apt-daily`** 가 33초간 CPU 27.3초를 먹어 1코어를 포화시켰고
가드가 11:57:49 에 트립했다. 가드는 제 역할을 했다(코어 포화는 사실). 이후 런에서는 해당
타이머를 정지시키고 진행했다.

## 4. 각 방향 18 Mbps — 21분 12초에 붕괴

16:07:43 시작, 16:28:55 가드 트립. 클라이언트 집계는 SIGKILL 로 유실됐으나 **s 서버측
로그가 살아남아 1초 해상도 1,247초 전체**를 확보했다(가드 패턴이 `iperf3 -c` 라 서버는
안 죽었다).

### 4-가. 손실이 시간에 따라 커진다

| 구간 | 실효 | 손실 | 최악 1초 |
|---|---|---|---|
| 0~299s | 17.99 | 0.0246% | 3.38% |
| 300~599s | 17.98 | 0.0810% | 11.16% |
| 600~899s | 17.99 | 0.0675% | 7.17% |
| **900~1199s** | 17.93 | **0.3851%** | **41.80%** |
| 1200~1246s | 18.00 | ~0% | 0.11% |

**전반 0.0508% → 후반 0.2175% (4.3배).** 실효는 17.98 Mbps 로 끝까지 유지됐다 —
**무너진 것은 처리량이 아니라 손실이다.** 손실은 균등하지 않고 버스트다: 1,247초 중
284초에만 실손실이 났고 최악 1초에 818패킷이 날아갔다.

계단 18 단계는 c→s 손실 **0%** 였다.

### 4-나. 같은 부하인데 CPU 가 오른다

```
16:08  55.1%   16:15  69.0%   16:22  62.9%   16:27  58.5%
16:09  55.9%   16:16  64.9%   16:23  66.1%   16:28  64.5%
16:10  55.4%   16:17  64.9%   16:24  64.9%
16:12  56.6%   16:18  53.0%   16:26  66.9%
```

첫 5분 ~56% → 마지막 5분 ~65%. 프로세스 CPU 71.4→74.3%(+2.9p), 시스템 busy
54.8→58.5%(+3.7p) 로 함께 올랐다.

**열은 배제된다** — c thermal zone **26°C**, thermal event 인터럽트 **0건**,
governor `schedutil`, `bios_limit` = 정격 1,600,000. 스로틀링 흔적이 없다.

**원인 미규명.** 손실 증가와 CPU 증가가 동행해 인과 방향을 이 데이터로는 가를 수 없다.

### 4-다. 가드는 부하 자체에 트립했다

초과 **37건 중 30건이 `c:전체>62%`**(나머지 6건은 `r:1코어`). 3연속에서 트립:

```
16:28:53 초과(2/3): c:전체=72.9%>62%
16:28:54 초과(2/3): c:전체=64.7%>62%
16:28:55 초과(3/3): c:전체=67.2%>62%
16:28:55 트립 → 'iperf3 -c' 중단
```

3-다 와 달리 이번은 **정당한 트립**이다. 임계 62% 는 용량 모델의 실측 포화점이고,
지속 18 Mbps 는 그 예산을 실질적으로 넘는다.

### 4-라. 누수는 판정 불가

c 11.8→13.2 MB, s 13.0→14.0 MB, r 0.8 고정. **21분은 램프도 못 끝낸 길이**라(§3-가에서
램프 약 20분) 이 기울기로 누수를 판정하면 틀린다. **FD 는 전 호스트 고정**(8/14/8).

## 5. 각 방향 12 Mbps — 1시간 완주, 전 항목 통과

17:29:24 ~ 18:29:24, 3600초 전부. 가드 초과 6건 / **트립 0**.

### 5-가. 손실

```
c→s   0 / 4,326,923 = 0.00000%     (전반 30분 0, 후반 30분 0)
s→c  74 / 4,326,922 = 0.0017%
지터  0.778 ms       OoO 198,305
```

10분 버킷 6개 전부 0(±1패킷은 재정렬):

```
   0~ 599s  0.00000%      1800~2399s  0.00000%
 600~1199s  0.00014%      2400~2999s  0.00000%
1200~1799s -0.00014%      3000~3599s  0.00000%
```

519초 구간에서 순간 손실로 잡힌 **564패킷은 전부 다음 초에 도착한 재정렬분**이다
(최대 1초 3패킷). **18 Mbps 에서 보인 시간 열화가 없다.**

> **일관성 확인**: OoO 198,305 ÷ 3,600s = **55.1/s**. 계단 12 단계는 2,465 ÷ 45s = **54.8/s**.
> 같은 값이다 — 재정렬은 레이트에 딸린 정상 현상이고 시간에 누적되지 않는다.

### 5-나. CPU 평탄

```
c 전체      전반 42.7% → 후반 43.0%   최대 58.8% / 임계 62%
c 최고1코어  전반 62.8% → 후반 62.2%   최대 86.1% / 임계 85%
r 전체      15.0% → 14.7%      s 전체  11.5% → 10.9%
```

18 Mbps 에서 21분간 +9포인트였던 드리프트가 **+0.3포인트**로 사라졌다. 그 드리프트는
시간 경과 자체가 아니라 **부하 수준에 딸린 현상**이다.

> ⚠️ **최고1코어가 최대 86.1% 로 임계 85 를 스쳤다**(초과 6건, 전부 단발이라 무트립).
> 평균은 62%대지만 순간 스파이크는 상한에 닿는다. 12 가 여유로운 점은 아니다.

### 5-다. 누수 없음 (고부하 최초 확인)

| | RSS | 마지막 30분 기울기 | FD |
|---|---|---|---|
| c 클라이언트 | 13.2 → 13.2 MB | **+0.00 MB/h** | 8 고정 |
| r 릴레이 2 | 0.8 → 0.8 MB | **+0.00** | 14 고정 |
| s 서버 | 14.0 → 14.0 MB | **+0.00** | 8 고정 |

## 6. 트래픽 격납 — 3개 런 전부 깨끗

전 호스트 전 인터페이스를 유휴 60초와 부하 구간으로 각각 재서 차분했다. 12 Mbps 런:

```
앱(WG 터널)   c starlink-fec 25.20 / s starlink-fec 25.20 Mbps   ← 양단 일치
전송 계층     c enp2s0 66.31 · r ens18 133.41 · s ens18 67.28
증폭          66.31 / 25.20 = 2.63배 (duplicate 2경로 × FEC)
```

그 외 **전 인터페이스 ±0.000 Mbps** — c 의 LTE(`enp3s0`, 2026-08-07 신설), `starlink-xdn`,
r 의 docker0/br-*/veth×3, s 의 공인 `ens19`/`ens20` 전부 유휴 유지. r 이 c 의 2배인 것은
수신·전달이 같은 ens18 을 두 번 지나기 때문으로 정상이다.

회선은 1 GbE 의 **6.6%**(12M) / 9.7%(18M) 밖에 안 쓴다 — **병목은 c 의 CPU 단독**이다.

> `starlink-fec` 는 부하가 **실제로 흐르는 WG 터널**이다(규칙 1). 외부 유출이 아니라 앱
> 계층 그 자체이고, 여기서 multi-fec 을 거쳐 물리 인터페이스로 나갈 때 증폭이 붙는다.
> 분석기 초판이 이걸 "외부" 로 오분류했다 — 격납 판정 로직을 쓸 때 계층을 구분할 것.

## 7. 하네스 결함 4건 (전부 이번에 만든 것)

### 7-가. 운영 클라이언트를 죽였다 (실제 피해)

`mf_aging_1h.sh` 정리 패턴을 2026-08-03 원본의 `127.0.0.1:518[6-9]` 에서 `127.0.0.1:518` 로
줄여 썼다. 시험 클라는 51861~51868 이지만 **운영은 51821** 이라 같이 매치된다.
c 의 `multi-fec-client` 가 11:57:55~12:17:42 **약 20분간 정지**했다. 복구했고 범위를
되돌린 뒤 이유를 주석으로 박았다.

### 7-나. bracket 패턴이 같은 커맨드라인 뒤쪽에서 무력화된다 ★ 새 변종

```bash
ssh $S "pkill -9 -f '[i]perf3 -s'; ... setsid nohup iperf3 -s -B 10.9.10.1 ... &"
#              └ 브래킷으로 가린 토큰            └ 여기 평문이 그대로 있다 → 자기 셸 매치
```

bracket 은 **그 토큰만** 가려준다. 같은 커맨드라인 뒤쪽에 평문 `iperf3 -s` 가 있으면
정규식이 그걸 매치해 `pkill -9` 가 자기 셸을 죽인다. **실측 `ssh rc=255`, 서버 미기동,
로그 파일만 빈 채 생성.** → **kill 과 기동을 별도 ssh 로 분리**해야 한다.

기존 함정 #1·#7 의 변종이다. #1 은 "패턴을 인자로 준 셸", #7 은 "가드 자신의 argv" 였고,
이번은 **같은 명령 안의 다른 문장**이다.

### 7-다. `nohup ... &` 만으로는 원격 데몬이 안 산다

ssh 채널이 닫힐 때 같이 죽어 **로그 파일조차 안 생겼다.** `setsid` + `</dev/null` 이
필요하다.

### 7-라. `pgrep -cf` 는 미매치 시 `0` 을 찍고 exit 1

`$(ssh ... "pgrep -cf ..." || echo 0)` 이 `"0\n0"` 이 되어 `[ ]` 정수 비교가 깨진다.
`| head -1` 로 첫 줄만 취한다. 진짜 원인(7-나)의 진단을 가렸다.

### 7-마. 그 외 관측

- **가드가 트립하면 부하 생성기의 최종 집계가 유실된다**(SIGKILL). 3-나·4 에서 둘 다 겪었다.
  집계를 **수신측에도** 남겨두면 살아남는다 — §4 를 구한 것이 s 의 iperf3 서버 로그였다.
- `run_in_background` 로 띄운 래퍼가 끝날 때 자식이 같이 죽는 경우가 있었다. `setsid` 로
  프로세스 그룹을 분리해 해결.

## 8. 정정된 운용 권장

**지속 부하 근거가 있는 값은 12 Mbps 뿐이다.** 나머지는 45초 버스트 값이고, 18 이 21분에
무너진 이상 그대로 쓸 수 없다.

| 용도 | 앱 각 방향 | 양방향 | 회선 | 근거 |
|---|---|---|---|---|
| **지속 운용 (검증됨)** | **12 Mbps** | 24 | 66 Mbps | 1시간, 손실 0 / 0.0017%, CPU 평탄, 누수 0 |
| 단시간 버스트 | ~22 Mbps | 44 | 118 | 45초 계단 — **지속 불가 확인됨** |
| 지속 상한 | **12 < X < 18** | — | — | **미측정** |

**2026-08-06 REPORT §9 의 "실용 한계 22 Mbps" 는 버스트 한계로 읽어야 한다.** 그 문서를
개작하지 않고 이 문서로 보완한다(측정 보고서 사후 개작 금지 관례).

## 9. 미해결

1. **지속 한계의 정확한 위치** — 14 나 16 이 1시간을 버틸 수도 있다. 한 번씩 더 돌리면 좁혀진다.
2. **18 Mbps 의 CPU 드리프트 원인** — 열은 배제됐고 12 에서는 재현되지 않는다. 손실↑와 CPU↑가
   동행해 인과를 못 가른다. 후보: FEC 복구 작업량 증가, 재정렬 누적, dedup/decode-buf 거동.
3. **다중 세션 지속 한계** — 이번 고부하 런은 전부 단일 인스턴스다. 8세션 런은 저레이트였다.
4. **오배송 직접 검증** — §3-나 참조. 태그 집계가 유실됐다.

## 10. 절차 (재현)

```bash
cd test-results/2026-08-07-aging-1h

# 저부하 다중 세션 에이징 (8세션 × 각 0.25 Mbps, 병렬 체인 :4443)
N=8 SECS=3600 MBPS=0.25 setsid nohup ./mf_aging_1h.sh > run.log 2>&1 < /dev/null &
python3 analyze.py

# 지속 소크 (단일 인스턴스, 운영 체인 :443) — RATE 는 앱 각 방향 Mbps
RATE=12 OUT=$PWD/soak12 setsid nohup ./mf_soak_18m.sh > soak12_run.log 2>&1 < /dev/null &
ssh s.xdn.selfinet.com 'cat /tmp/sk_srv.log' > soak12/iperf_server.log   # 1초 해상도 (수신측)
python3 analyze_soak.py soak12
```

두 하네스 모두 **가드를 스스로 띄우고**, precheck 실패 시 부하를 시작하지 않는다.
`mf_soak_18m.sh` 는 r 의 `apt-daily-upgrade.timer` 를 정지시키고 정리 시 복구한다
(systemd 예약 백업 포함).
