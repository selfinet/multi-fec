## 0. 결론

**주장은 사실이고, 릴레이 쪽은 문서보다 나쁘다.**

| | 결과 |
|---|---|
| 프로세스 1개 장애 (path[0]) | ✅ **공백 0** — 응답 99.4%, RTT 54.2 → 64.2 ms 로 path[1] 절체 |
| **프로세스 2개 동시 = 호스트 장애 대리** | ❌ **연속 공백 27.94초** — 응답 3.1% |

| 서버 SPOF | 확인 — 한 호스트. 10지사 구조에서 프로세스 10개가 모두 이 1대 |
| **부수 발견 (제품 결함)** | **클라이언트 pending 큐에 TTL 이 없다** — 복구 시 **26.5초 묵은 패킷**이 배달된다 |

## 1. 전제 확인 — 릴레이는 세 겹으로 공유된다

```
r (infra, QEMU VM)
  ens18   UP   192.168.100.85/24  192.168.100.86/24   ← 같은 인터페이스의 두 IP
  NIC 큐  rx-0 tx-0                                    ← 단일 큐
  프로세스 pid 364888 (.85:443) · pid 364889 (.86:443)
```

문서는 *"두 경로가 릴레이 호스트 `r` 과 스위치·L2 를 공유한다"* 고만 적었다. 실제로는 **같은 NIC 의 두 IP + 단일 큐**다. 공유 층위가 셋이다:

1. **커널·전원·VM** — 호스트가 죽으면 두 경로 동시 소멸
2. **NIC `ens18`** — 링크 장애 하나로 두 경로 동시 소멸
3. **단일 큐 `rx-0/tx-0`** — 가용성뿐 아니라 **성능 SPOF** 까지 겸한다(수신 softirq 가 한 코어에 고정 — 이것이 [최대 성능 측정](../2026-09-05-maxperf/REPORT.md)의 병목이었다)

서버는 `xdn-temp-pop` 한 호스트다. 목표 구조는 프로세스 10개를 **이 1대**에 올린다.

## 2. 방법

`spof_test.sh` — 프로브는 WG IP 사이 ping **5 pps**(규칙 1). 부하 시험이 아니라 가드는 띄우지 않았다.

```
 21.0s  A: 릴레이 1개 정지 (multi-fec-relay = path[0] .85)
 52.5s  A: 복구
 83.5s  B: 릴레이 2개 동시 정지  ← 호스트 장애 대리
109.4s  B: 복구
```

호스트를 실제로 정지시키지 않고 **두 프로세스 동시 정지**로 대리했다. 커널·NIC 층위의 동시 소멸을 재현하지는 못하지만, **"두 경로가 함께 사라진다"** 는 결과는 같다.

## 3. 결과

| 구간 | 응답 | RTT p50 | 해석 |
|---|---|---|---|
| 정지 전 | 100/100 (100%) | **54.2 ms** | 기준 |
| **A: path[0] 정지 중** | 157/158 (**99.4%**) | **64.2 ms** | **공백 0.** RTT 가 netem path[1](편도 30ms = RTT 60ms)로 이동 — 절체의 직접 증거 |
| A: 복구 후 | 154/155 (99.4%) | 54.3 ms | path[0] 복귀 |
| **B: 두 경로 정지 중** | **4/130 (3.1%)** | — | **연속 공백 27.94초** |
| B: 복구 후 | 서비스 재개 | 54.5 ms | **첫 응답 +2.76초** |

**A 는 duplicate 가 설계대로 커버한다** — 유실 1개는 절체 순간의 인플라이트다. [2026-08-03 릴레이 단절 측정](../2026-08-03-pathcorr-relaycut/REPORT.md)의 "duplicate 공백 0"을 다시 확인했다.

**B 는 전면 단절이다.** 공백 27.94초 = 단절 25.9초 + 회복 2.8초. **경로 2개는 프로세스 장애만 분리한다는 주장이 실측으로 확정됐다.**

**복구는 자동이고 2.8초다** — 릴레이가 살아나면 mud 가 경로를 DEGRADED → RUNNING 으로 되돌린다. 수동 개입이 필요하지 않다.

## 4. ⚠️ 부수 발견 — 클라이언트 pending 큐에 TTL 이 없다 (제품 결함)

복구 직후 첫 응답의 RTT 가 **26,574 ms** 였고, 이후 응답이 **204 ms 씩 정확히 감소**했다(26574 → 26370 → 26166 → …). 204 ms 는 프로브 간격 200 ms 다 — **단절 중 쌓인 약 130개가 FIFO 로 한꺼번에 배출된 것**이다.

코드를 확인했다:

```c
/* mf_server.cpp */
#define SERVER_PENDING_TTL_MS 1000
struct ... { my_time_t ts;   /* enqueue time, for the TTL above */ ... };

/* mf_client.cpp */
struct pending_pkt_t { char data[...]; int len; };   ← 시각 필드가 없다 = TTL 없음
```

**서버 pending 큐는 v1.0.2(§19-라)에서 TTL 1초를 받았는데 클라이언트 큐는 못 받았다.** 그래서 클라이언트는 경로가 전부 죽은 동안 최대 `PENDING_Q_CAP`(512)개를 무기한 보관하고, 복구 시 전부 내보낸다.

**영향**: 단절 복구 직후 터널에 **수십 초 묵은 패킷 최대 512개**가 주입된다. 터널 안 TCP 에게는 이미 재전송이 끝난 중복 세그먼트이고(dup-ACK·재정렬 유발), 실시간 트래픽에는 쓰레기다. 게다가 **새 패킷이 그 뒤에 줄을 선다**.

**제안 수정**(제품 코드라 이번에 적용하지 않았다): `pending_pkt_t` 에 `ts` 를 넣고 `flush_pending_packets()` 에서 서버와 같은 1초 TTL 로 폐기. 서버측 구현이 이미 있어 대칭으로 맞추면 된다. 와이어 무변경, 클라이언트 단독 수정.

## 5. 해소 가능성 — 현 테스트망에서는 불가

호스트가 `c`·`r`·`s` 셋뿐이다. 릴레이를 다른 호스트로 옮기려면 `c` 나 `s` 에 올려야 하는데, 그러면 **릴레이가 클라이언트 또는 서버 호스트와 운명을 공유**해 분리가 아니다. [2026-08-02 REPORT §7](../2026-08-02-50mbps-soak/REPORT.md)의 "현 테스트망에서는 해소 불가" 판단은 여전히 유효하다.

**실서비스에서 해야 할 것**(검증이 아니라 설계 사항):

| SPOF | 조치 |
|---|---|
| 공유 릴레이 호스트 | 릴레이 2 인스턴스를 **다른 호스트**에. 최소한 다른 NIC — 지금은 같은 NIC 의 두 IP 라 링크 하나가 두 경로를 지운다 |
| 서버 호스트 | 프로세스 10개는 **고장 격리를 주지 않는다**. 호스트 이중화 또는 지사 그룹별 분산 |
| (부수) 단일 큐 | 성능 병목이기도 하다. 멀티큐 NIC 이면 수신 softirq 가 분산된다 |

**단절 27.94초 = 릴레이 호스트 장애 시 예상 서비스 중단 시간**이다(장애 감지·복구 시간은 별도). 이 값이 SLA 로 받아들일 수 있는지가 이중화 투자 판단의 기준이 된다.
