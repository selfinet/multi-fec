## 1. 왜 다시 쟀나 — 앞선 다중 세션 시험은 WG 가 없었다

같은 날 오전에 돈 `mf_multi_soak.sh`(4세션 × 4 Mbps)에는 **WireGuard 가 하나도 없었다.**

```
(오전, 잘못된 구조)  blaster → multi-fec client → relay×2 → server → rt_echo
```

하네스에 보이는 `--wg 127.0.0.1:44444` 는 **multi-fec 의 옵션 이름**일 뿐 실제 WG 가 아니라
Python echo 를 가리킨다. 그런데 실서비스는 **지사마다 독립 WG 터널**이라 세션 수만큼 암복호가
붙는다. 그 비용이 빠진 측정은 낙관적으로 치우친다.

> **사용자 지적으로 발견했다.** 그 전까지 문서에는 "병렬 체인에는 WG 가 없어 단일 세션과 CPU
> 비교 불가"라는 주의만 달려 있었는데, 실제 문제는 비교 가능성이 아니라 **목표 구조를 재현하지
> 못한 것**이었다.

       c: Endpoint=127.0.0.1:5190{i}                s: ListenPort=5190{i}

### 3-나. CPU — c 가 압력을 받지만 버틴다

| | 값 |
|---|---|
| c 머신 busy (10초 창 평균) | **49.7%**, 최대 55.7%, 드리프트 **+0.7p** |

두 값이 다른 이유는 **창 길이**다 — 가드는 1초, 샘플러는 10초 평균이라 순간 피크가 가드에만
보인다. 초과 30건은 c 가 임계선 근처에서 흔들렸다는 뜻이고, 실제로 이번이 지금까지
**가드 초과가 가장 많았던 런**이다.

**CPU 분해** (논리 CPU 4개 기준):

```
multi-fec 클라 10개   1.06 논리CPU   (프로세스 CPU 합 105.6%)
부하 생성기            0.18          (mf_blast, 18.0%)
나머지                 0.75          ← WG 암복호 10개 + 수신 softirq + 시스템
──────────────────────────────
머신 총계              1.99 논리CPU  (= 49.7% × 4)
```

**WG + softirq 가 전체의 38% 를 쓴다.** 오전의 WG 없는 시험이 놓친 부분이 이것이다.

> ⚠️ **생성기 0.18 논리CPU 는 실서비스에 없는 비용**이다. 제품만의 몫은 약 1.81 논리CPU 다.
> 반대로 실서비스에서는 지사 10곳이 **각자 다른 호스트**이므로 클라 측 1.06 은 10대에 나뉜다 —
> 이 시험은 c 한 대가 지사 10곳을 흉내낸 **최악 조건**이다.

### 3-다. 자원

| 호스트 | 프로세스 | RSS | 마지막 15분 | FD |
|---|---|---|---|---|
| c | 클라 10 | 111.4 → **130.6 MB** (13.1/개) | **+0.00 MB/h** | 70 (7/개) |

> 10연결 = 130 MB 이므로 **10지사 서버 호스트 메모리 산정은 100 MB 가 아니라 130 MB** 로 본다.

## 3-바. 90분 소크 — 누수 재검증 (2026-09-04 11:53 ~ 13:23)

**"CPU·메모리가 누수되거나 계속 증가하는가"** 에 답하기 위해 같은 구성으로 90분을 돌렸다.
1시간 런보다 **판정 구간이 50분 → 70분**으로 길어진다(램프는 여전히 첫 10~20분).

| 항목 | 결과 |
|---|---|
| 왕복 전달 | **5,624,985 / 5,625,000 = 99.9997%** (유실 15) |
| **오배송** | **0** — 10세션 전부 |
| 완주 | ✅ 5400초 · 가드 초과 23 · **트립 0** · 무감시 구간 0 |
| 생성기 | `pacing_resets=0` · `sendfail=0` |
| 증폭 | 3.43배 (1시간 런 3.46 과 일치) |

### 메모리 — 누수 아니다. 계단 2개 뒤 완전 평탄

**RSS 는 연속 증가가 아니라 계단 함수**다. 램프(첫 20분) 이후 70분 동안:

| 호스트 | 총 증가 | 값이 바뀐 횟수 | 계단 위치 | **마지막 평탄 구간** |
|---|---|---|---|---|
| c (클라 10) | **+0.28 MB** (+0.21%) | **2회** | 25분 +0.15 · 43분 +0.13 | **마지막 47분 1 KB 불변** |
| s (서버 10) | **+0.62 MB** (+0.48%) | **2회** | 43분 +0.12 · 60분 +0.50 | **마지막 30분 1 KB 불변** |
| r (릴레이 2) | **−0.05 MB** (감소) | 1회 | 60분 −0.05 | 마지막 30분 불변 |
| 생성기 | **0** | 0회 | — | 전 구간 불변 |

**FD 는 전 호스트 완전 고정** — c 70, s 70, r 32, 생성기 13. 최소=최대=시작=끝.

> ⚠️ **선형회귀로 판정하면 틀린다.** 램프 이후 구간에 최소제곱을 걸면 c +0.193±0.015,
> s +0.769±0.035 MB/h 로 "0 을 포함하지 않는다"가 나온다. 그런데 **같은 판정이 생성기
> (+0.000±0.000)와 릴레이(−0.059, 감소)에도 나온다.** RSS 가 계단이라 잔차가 작아 회귀가
> 과신하는 것이다. **계단 개수와 마지막 평탄 구간으로 봐야 한다** — 누수라면 계단이
> 계속 쌓여야 하는데 c 는 43분 이후 47분간, s 는 60분 이후 30분간 **1 KB 도 안 움직였다.**

계단의 정체는 확인하지 않았다. 크기(0.12~0.50 MB)와 빈도로 보아 allocator arena 확장이나
주기적 버퍼로 보이나 **추정이다.**

### CPU — 워밍업 후 평탄, 후반은 오히려 하락

6구간 평균(프로세스 CPU 합, 논리 CPU 1개 = 100%):

| | 1 | 2 | 3 | 4 | 5 | 6 | 1→6 |
|---|---|---|---|---|---|---|---|
| c (클라 10) | 104.3 | 106.4 | 106.4 | 106.5 | 106.4 | **106.2** | +2.0 |
| r (릴레이 2) | 40.0 | 41.2 | 41.3 | 41.5 | 41.5 | **41.3** | +1.3 |
| s (서버 10) | 44.2 | 45.1 | 44.8 | 44.9 | 44.9 | **44.9** | +0.7 |
| 생성기 | 17.8 | 17.9 | 17.9 | 17.9 | 17.9 | **17.8** | +0.1 |
| **c 머신 busy** | 48.6 | 49.7 | 49.6 | 49.8 | 49.5 | **49.3** | +0.7 |

**증가분은 전부 구간1 → 구간2 에서 나오고 그 뒤는 평탄하다.** 구간 2~6 은
106.4 / 106.4 / 106.5 / 106.4 / 106.2 로 **마지막 두 구간이 오히려 내려간다.**
단조 증가 곡선이 아니다.

### 판정

**90분 구간에서 CPU·메모리 누수는 없다.** 다만 이 결론의 한계를 분명히 한다:

- **시간당 0.1 MB 미만의 느린 누수는 90분으로 검출할 수 없다.** c 의 관측 상한
  (+0.28 MB / 70분)을 그대로 외삽하면 24시간에 5.8 MB 인데, **마지막 47분이 완전 평탄이므로
  이 외삽은 성립하지 않는다.** 진짜 상한을 알려면 24~72시간이 필요하다.
- 지금까지의 최장 관측은 **5시간**(2026-08-02, 단일 체인 6 Mbps)이고 거기서도 RSS 가
  변하지 않았다. **다중 세션 구성의 최장은 이번 90분이다.**

## 5. 하네스

새로 만든 것 — `mf_wg_multi.sh`(203줄), `mf_blast.c`(C 부하 생성기), `rt_echo_ip.py`.

**`mf_blast` 가 Python 생성기를 대체한 이유는 CPU 가 아니라 격리다.** sv1 A/B 에서 Python 도
레이트는 정확히 냈다(22% vs C 17%). 다만 C 판은 RSS 0.77 MB 로 가볍고, 이번 런에서
**생성기 비용 0.18 논리CPU 를 분리 계측**할 수 있게 해줬다 — 그게 실제 이득이었다.

### 이번에 잡은 하네스 결함 3건

**① 가드가 트립하면 나머지 런이 무감시가 된다** (오전 4×4 런에서 실제 발생).
트립 시각에 대상 프로세스가 아직 없으면 아무것도 못 죽이고 가드가 종료한다 → 그대로 1시간을
무감시로 돌았다. **부하와 병렬로 가드 생존을 감시하고 사라지면 부하를 중단**하도록 고쳤다.
이번 런에는 `guard_died.log` 가 없다.

**② 샘플러 패턴이 운영 프로세스를 함께 센다.** kill 패턴은 `518[6-9]` 로 고쳐져 있었는데
**샘플러 패턴은 `518` 그대로**였다 — 운영 클라(:51821)와 운영 릴레이(.85:443)가 합산돼
누수 판정이 무의미해진다. 양쪽에 포트 범위를 넣었다. 이번 런은 `nproc` 이 정확히 10/10/2 다.

**③ 샘플러 패턴이 실제 cmdline 과 안 맞았다.** `mf_blast --sessions` 로 잡으려 했으나 실제는
`mf_blast --no-clients --sessions …` 라 **사이에 낀 옵션 때문에 매치 실패** → CSV 가 헤더만
남았다. 패턴을 이름만으로 줄였다(래퍼 셸은 `comm` 필터가 걸러낸다).

> 세 건 모두 **조용히 틀린 값을 내는** 종류다. 크래시하지 않고 그럴듯한 결과가 나오므로
> 결과를 먼저 의심하지 않으면 발견되지 않는다.

| 순위 | 항목 | 비고 |
|---|---|---|
| 1 | **peak 프로파일 (지사당 10 Mbps × 10)** | 총 100 Mbps 앱. c 한 대로는 불가 — 세션 수를 줄이거나 부하를 나눠야 한다 |
