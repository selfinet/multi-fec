
RSS 상승분은 **연결당 FEC 링버퍼의 lazy 할당**(`--decode-buf 2000` = 연결당 9.4 MB 상한)이

전구간 기울기는 c 가 +20.99 MB/h 로 보이지만 그것은 램프를 회귀에 넣은 결과이고,
후반 절반은 +0.69 MB/h, 마지막 계단 이후는 **0**이다.

## 3. 결과 — pending 큐 TTL 경로 (이번 수정의 실제 코드)

**일반 소크는 이 코드를 한 번도 실행하지 않는다.** pending 큐는 mud EAGAIN·경로 단절에서만
쓰이므로, 2026-09-09 SPOF 시험의 조건(릴레이 2개 동시 정지 → 복구)을 반복 재현했다.
`pendttl_test.sh` — 프로브는 WG IP 간 ping 5 pps(규칙 1), 단절 26초 · 정착 35초 × N사이클.

### 3-가. A/B — 같은 스크립트, 클라이언트 바이너리만 교체

| | **v1.3.0** (2사이클) | **v1.3.1** (3사이클) |
|---|---|---|
| 복구 후 첫 응답 RTT | **27,007 / 27,014 ms** | **1,978 / 1,937 / 2,026 ms** |
| 1초 초과 응답 수 | **60개 이상**(관측 창 60개가 전부 초과) | **5~6개** |
| 클라 stale 폐기 | **0회** (기능 없음) | **413회 / 745개** |
| 클라 flush | 2회 / **524개** | 3회 / 33개 |

v1.3.0 은 단절 길이 그대로(27초)의 묵은 패킷을 배달하고 RTT 가 프로브 간격(204 ms)씩
감소한다 — 09-09 관측(26,574 ms)의 재현이다. v1.3.1 은 그 꼬리가 사라졌다.

### 3-나. 남은 2초는 클라이언트 큐가 아니다 — **서버 큐**다

v1.3.1 의 2초를 송신 시각으로 귀속시켰다(`송신 = 수신 − RTT`).

```
cycle1  복구 기준   수신        송신        RTT
        +1.77s     -0.20s     1978 ms   ← 단절 중 송신, 나이 200 ms (TTL 안, 정상 전송)
        +1.77s     +0.00s     1774 ms   ← 복구 후 송신
        +1.78s     +0.61s     1163 ms   ← 복구 후 송신
        +1.78s     +1.22s      552 ms   ← 복구 후 송신
```

**응답이 모두 한 시점(+1.77~2.07s)에 몰려 도착하고 송신 시각은 거의 전부 복구 이후**다.
즉 클라이언트가 묵은 패킷을 내보낸 것이 아니라(그건 745개가 폐기됐다), **복구 직후 보낸
새 패킷이 귀환 경로에서 한 번에 풀린 것**이다. 단일 flush 이벤트의 서명이다.

원인은 코드에 있다 — `mf_server.cpp` `flush_server_pending()` 은 `SERVER_PENDING_TTL_MS`
를 **`mud_send` 가 실패했을 때만** 본다. 성공 경로에는 나이 검사가 없어, 경로가 살아나는
순간 큐 전체가 나이와 무관하게 나간다.

```c
int ret = mud_send_mp(g_mud, p.data, p.len, p.peer);
if (ret < 0) {                       /* ← TTL 은 이 안에서만 확인된다 */
    if (now - p.ts <= SERVER_PENDING_TTL_MS) break;
    ...
}
```

**이번 릴리스에서 고치지 않았다** — 서버측 수정은 별개 변경이고 자체 검증이 필요하다.
제안: 클라이언트와 같은 형태로 **전송 전** 나이 검사를 두는 것(와이어 무변경, 서버 단독).
현 상태에서도 클라이언트 수정만으로 **최악 배달 나이가 27초 → 2.1초**로 내려간다.

단절→복구를 3회 반복하며 클라이언트 프로세스(PID 고정)를 관측했다.

| 시점 | RSS | FD |
|---|---|---|
| before | 11.46 MB | 8 |
| cycle1 | 12.37 MB | 8 |
| cycle2 | 13.40 MB | 8 |
| cycle3 | **13.40 MB** | 8 |
| after | **13.40 MB** | 8 |

두 사이클에서 고원에 도달해 이후 **1 KB 도 움직이지 않는다**. `pending_pkt_t` 배열은

v1.3.0 도 같은 궤적(11.19 → 13.73 MB, FD 8 고정)이라 **이번 변경이 더한 상주는 없다**.

## 6. 이 시험이 말하지 않는 것

- **30분은 누수 검출 창으로 짧다.** v1.3.0 은 24시간(검출 한계 약 0.005 MB/h)으로 확인됐고
  이번은 그 수준이 아니다. 근거는 "v1.3.0 궤적과 겹친다"는 **대조**이고, 절대적 장기
  안정성의 재확인이 아니다. 서비스 적용 전 장기 확인을 원하면 24시간 런을 다시 돌려야 한다.
- **서버측 pending 나이 검사는 여전히 없다**(§3-나). 단절 복구 시 최대 약 2초의 묵은
  하향 패킷이 남는다.
- 사이클 시험은 5 pps 프로브다. 고레이트에서 큐가 꽉 찬 상태(512 엔트리)의 거동은
  이번에 재지 않았다.
