## 3. 결과 — pending 큐 TTL 경로 (이번 수정의 실제 코드)

**일반 소크는 이 코드를 한 번도 실행하지 않는다.** pending 큐는 mud EAGAIN·경로 단절에서만
쓰이므로, 2026-09-09 SPOF 시험의 조건(릴레이 2개 동시 정지 → 복구)을 반복 재현했다.
`pendttl_test.sh` — 프로브는 WG IP 간 ping 5 pps(규칙 1), 단절 26초 · 정착 35초 × N사이클.

### 3-가. A/B — 같은 스크립트, 클라이언트 바이너리만 교체

| | **v1.3.0** (2사이클) | **v1.3.1** (3사이클) |
|---|---|---|
| 복구 후 첫 응답 RTT | **27,007 / 27,014 ms** | **1,978 / 1,937 / 2,026 ms** |
| 1초 초과 응답 수 | **60개 이상**(관측 창 60개가 전부 초과) | **5~6개** |
| 클라 stale 폐기 | **0회** (기능 없음) | **413회 / 745개** |
| 클라 flush | 2회 / **524개** | 3회 / 33개 |

v1.3.0 은 단절 길이 그대로(27초)의 묵은 패킷을 배달하고 RTT 가 프로브 간격(204 ms)씩
감소한다 — 09-09 관측(26,574 ms)의 재현이다. v1.3.1 은 그 꼬리가 사라졌다.

### 3-나. 남은 2초는 클라이언트 큐가 아니다 — ~~**서버 큐**다~~ (§9 에서 반증됨)

v1.3.1 의 2초를 송신 시각으로 귀속시켰다(`송신 = 수신 − RTT`).

```
cycle1  복구 기준   수신        송신        RTT
        +1.77s     -0.20s     1978 ms   ← 단절 중 송신, 나이 200 ms (TTL 안, 정상 전송)
        +1.77s     +0.00s     1774 ms   ← 복구 후 송신
        +1.78s     +0.61s     1163 ms   ← 복구 후 송신
        +1.78s     +1.22s      552 ms   ← 복구 후 송신
```

**응답이 모두 한 시점(+1.77~2.07s)에 몰려 도착하고 송신 시각은 거의 전부 복구 이후**다.
즉 클라이언트가 묵은 패킷을 내보낸 것이 아니라(그건 745개가 폐기됐다), **복구 직후 보낸
새 패킷이 귀환 경로에서 한 번에 풀린 것**이다. 단일 flush 이벤트의 서명이다.

원인은 코드에 있다 — `mf_server.cpp` `flush_server_pending()` 은 `SERVER_PENDING_TTL_MS`
를 **`mud_send` 가 실패했을 때만** 본다. 성공 경로에는 나이 검사가 없어, 경로가 살아나는
순간 큐 전체가 나이와 무관하게 나간다.

```c
int ret = mud_send_mp(g_mud, p.data, p.len, p.peer);
if (ret < 0) {                       /* ← TTL 은 이 안에서만 확인된다 */
    if (now - p.ts <= SERVER_PENDING_TTL_MS) break;
    ...
}
```

> ⚠️ **이 절의 귀속은 틀렸다.** v1.3.2 로 서버 큐를 고쳤는데 2초가 그대로였고,
> 계측 결과 원인은 **WireGuard 재핸드셰이크**였다 → §9.

**이번 릴리스에서 고치지 않았다** — 서버측 수정은 별개 변경이고 자체 검증이 필요하다.
제안: 클라이언트와 같은 형태로 **전송 전** 나이 검사를 두는 것(와이어 무변경, 서버 단독).
현 상태에서도 클라이언트 수정만으로 **최악 배달 나이가 27초 → 2.1초**로 내려간다.

단절→복구를 3회 반복하며 클라이언트 프로세스(PID 고정)를 관측했다.

## 6. 이 시험이 말하지 않는 것

- **30분은 누수 검출 창으로 짧다.** v1.3.0 은 24시간(검출 한계 약 0.005 MB/h)으로 확인됐고
  이번은 그 수준이 아니다. 근거는 "v1.3.0 궤적과 겹친다"는 **대조**이고, 절대적 장기
  안정성의 재확인이 아니다. 서비스 적용 전 장기 확인을 원하면 24시간 런을 다시 돌려야 한다.
- **서버측 pending 나이 검사는 여전히 없다**(§3-나). 단절 복구 시 최대 약 2초의 묵은
  하향 패킷이 남는다.
- 사이클 시험은 5 pps 프로브다. 고레이트에서 큐가 꽉 찬 상태(512 엔트리)의 거동은
  이번에 재지 않았다.

## 7. 릴레이 2단 캐스케이드 스모크 (2026-09-10 23:54 → 09-11 00:24)

**동기**: 실서비스망이 `c ─ r 2단 × 2경로 ─ s` 인데 테스트망은 지금까지 **1단**만 돌렸다 —
캐스케이드는 v1.3.1 뿐 아니라 **어떤 버전으로도 측정된 적이 없었다.**

### 7-가. 배치 (호스트 3대로 두 홉을 모두 실제 회선으로)

```
c ─┬─► r .85:4443 (1단a) ─► s .84:4460 (2단a) ─┬─► s .84:4500+i (서버 i)
   └─► r .86:4443 (1단b) ─► s .84:4461 (2단b) ─┘
   c→r netem(25ms/5% · 30ms/2%) · r→s 온링크 · 2단→서버만 s 내부
```

각 홉이 HMAC 을 검증한다(1단은 전 키를 자기 짝 2단으로, 2단은 키별로 서버 분기) — 서비스
설정과 같은 구조다. 하네스 `mf_wg_cascade.sh`(운영 무침습 병렬 체인).
**재현되지 않는 것**: 홉별 물리 이중화(2단이 s 위에 있다), 원거리 2단의 지역 지연.

### 7-나. 결과 — 1단 구성과 나란히

| | 1단 (§2) | **2단 캐스케이드** |
|---|---|---|
| 전달 | 1,875,000 중 유실 **7** = 99.9996% | 1,875,000 중 유실 **7** = **99.9996%** |
| 오배송 / 손상 | 0 / 0 | **0 / 0** |
| 터널 RTT | 54.3 ms | **53.5 ms** (min 51.9, 손실 0%) |
| 가드 | 초과 2 · 트립 0 | 초과 2 · **트립 0** |
| c 클라이언트 RSS | 130.76 MB / FD 70 | **130.89 MB** / FD 70 |
| s 서버 RSS | 130.20 MB / FD 70 | **130.22 MB** / FD 70 |
| 1단 릴레이 (r) | 3.28 MB · 계단 0회 · FD 32 | **3.29 MB · 계단 0회 · FD 32** |
| **2단 릴레이 (s)** | — | **3.28 MB · 계단 0회 · FD 32** · CPU 36.1 → 36.3% |
| c 호스트 busy | 48.3 → 48.8% | 48.1 → 48.5% |
| s 호스트 busy | 16.8 → 15.7% | **24.7 → 24.7%** (2단 릴레이가 얹힘) |

**홉을 하나 더 지나도 손실·오배송·자원이 사실상 같다.** 릴레이가 raw bytes 투명 포워더라는
설계가 실측으로 확인된다. RTT 증가분은 온링크 `r→s`(편도 0.5~0.6 ms)뿐이라 1 ms 미만이다.

> ⚠️ **원거리 2단이면 그 구간 왕복이 그대로 더해진다.** 여기서 RTT 가 오르지 않은 것은
> 추가 홉이 같은 `/24` 안이기 때문이고, 실서비스 지연 예측에 쓸 수 없다.

### 7-다. 누수 판정 시 주의 — "마지막 변화 시각" 만 보면 오판한다

캐스케이드 런의 c 는 `마지막 변화 t=1813s → 평탄 0.0분` 으로 보고됐다. 그러나 그 말단 계단
2개는 **각 +0.01 MB(10 KB)** 이고, 0.75 MB 이상의 계단은 t=1075s 에서 끝났다.
`analyze_leak.py` 의 판정 지표가 **계단 크기를 보지 않는 것**이 원인이다.

```
1단        마지막 계단들: +0.88 / +0.76 / +0.77 / +0.13 / +0.13 MB  (t=1206s 종료)
캐스케이드 마지막 계단들: +0.25 / +0.26 / +0.75 / +0.01 / +0.01 MB  (실질 t=1075s 종료)
```

**교훈**: 계단 판정에는 **크기 하한**(예: 0.1 MB)을 두고 그 이상만 세야 한다. 10 KB 틱을
계단으로 세면 어떤 정상 런도 "평탄 0분" 이 된다. → [[measurement-harness-pitfalls]] §18 보강

## 8. 원거리 2단 캐스케이드 (2026-09-11 00:51 → 01:21)

§7 은 추가 홉이 온링크(편도 0.5 ms)라 **2단이 멀리 있는 경우**를 재현하지 못했다.
`r` 의 prio qdisc 에 `pref 3` 필터를 추가해 `r→s`(1단→2단) 트래픽을 기존 netem band 로
보냈다 — **홉마다 임피어먼트가 걸린다.** 하네스 `mf_wg_cascade_far.sh`.

```
path[0]  c→r 25ms/5%  +  r→s 25ms/5%   → 편도 50 ms, 상향 누적 손실 ≈ 9.75%
path[1]  c→r 30ms/2%  +  r→s 30ms/2%   → 편도 60 ms, 상향 누적 손실 ≈ 3.96%
```

> ⚠️ **단방향이다.** `s` 에는 netem qdisc 가 없어 `s→r` 은 무임피어먼트다(상향은 두 홉,
> 하향은 c↔r 만). `s` 의 `ens18` 에 root qdisc 를 새로 심는 것은 **운영 서버(:443)가 같은
> 인터페이스에 있어** 하지 않았다. 기존 `pref 1`(운영 경로)은 건드리지 않았고, 정리에서
> `mf-netem` 재시작으로 `pref 2·3` 이 소멸한다(런 후 잔존 0 확인).

### 8-가. 3열 비교

| | 1단 (§2) | 근거리 2단 (§7) | **원거리 2단 (§8)** |
|---|---|---|---|
| 전달 | 99.9996% (유실 7) | 99.9996% (유실 7) | **99.9969% (유실 59)** |
| 오배송 / 손상 | 0 / 0 | 0 / 0 | **0 / 0** |
| 세션별 최저 | 99.9989% | 99.9989% | **99.9936%** |
| 터널 RTT | 54.3 ms | 53.5 ms | **80.2 ms** (min 77.1, mdev 3.6) |
| 가드 | 초과 2 · 트립 0 | 초과 2 · 트립 0 | 초과 2 · **트립 0** |
| c 클라 | 130.76 MB · CPU 121→123% | 130.89 MB · 121→122% | **130.64 MB · 118→121%** |
| 1단 릴레이 | 3.28 MB · 계단 0 · FD 32 | 3.29 MB · 계단 0 · FD 32 | **3.28 MB · 계단 0 · FD 32** |
| 2단 릴레이 | — | 3.28 MB · 계단 0 · FD 32 | **3.29 MB · 계단 0 · FD 32** |
| s 서버 | 130.20 MB | 130.22 MB | **130.49 MB** |

### 8-나. 읽는 법

- **상향 누적 손실 9.75% 를 `-f 5:1,20:4` + duplicate 가 덮는다.** 유실이 7 → 59 로 8배
  늘었지만 전달률은 **99.9969%** 다. 프로브 ping 은 손실 0% 로 왕복했다.
- **RTT 증가분 26 ms** 는 단방향 임피어먼트(+25/30 ms 상향)와 일치한다. 즉 지연은 홉 수가
  아니라 **홉의 거리**가 정한다 — §7 에서 RTT 가 안 오른 이유이기도 하다.
- **자원은 세 런이 사실상 동일하다.** 릴레이 두 단 모두 30분 내내 RSS 변화 0회·FD 32 고정,
  클라·서버는 램프 후 같은 고원(130.5~130.9 MB). 손실이 8배인 조건에서도 변화가 없다.
- c CPU 가 오히려 낮다(118→121% vs 121→123%). 상향 손실이 커져 **서버에 도달하는 양이 줄고**
  하향 FEC 부담도 줄기 때문으로 보이나, 1초 창 편차(±5~9p) 안이라 단정하지 않는다.

### 8-다. 이 시험이 여전히 말하지 않는 것

- **하향 원거리 구간** — `s→r` 임피어먼트가 없다. 실서비스에서 2단이 원거리면 하향도 같은
  지연·손실을 받는다. 그때 duplicate 의 중복 누출은 `지연차 × pps` 로 커진다(여기서는
  지연차가 상향 10 ms 로 §7 과 같았다).
- **홉별 물리 이중화** — 2단이 `s` 위에 있다(호스트 3대 제약).
- 30분이라 누수 검출 창은 여전히 짧다(§6).

## 9. 정정 — 남은 2초는 multi-fec 이 아니라 **WireGuard 재핸드셰이크**다 (2026-09-11, v1.3.2)

§3-나 는 v1.3.1 의 잔존 2초를 **서버 pending 큐**로 귀속했다. 그 가설로 v1.3.2 를 만들어
`flush_server_pending()` 의 나이 검사를 전송 전으로 옮겼는데 — **결과가 바뀌지 않았다.**

| 사이클 시험 (단절 26초 × 3) | v1.3.0 | v1.3.1 | **v1.3.2** |
|---|---|---|---|
| 복구 후 첫 응답 RTT | 27,007 ms | 1,978 ms | **2,014 / 1,837 / 1,977 ms** |
| 1초 초과 응답 | 60개 이상 | 5~6개 | **5개** |
| 클라 stale 폐기 | 0 | 745개 | 756개 |

### 9-가. 계측으로 확정

`c` 에서 5 pps ping 과 **200 ms 간격 `wg show latest-handshakes`** 를 동시에 남기고 한 사이클을 돌렸다.

```
복구 기준   WG latest-handshake 갱신 : +2.03 s
            응답 6개 전부 도착        : +1.96 s     ← 같은 순간
            그 요청들의 송신 시각     : +0.01 ~ +1.03 s  (약 1초 폭)
```

**요청은 1초에 걸쳐 나갔는데 응답이 한 시점에 몰려 도착하고, 그 시점이 핸드셰이크 완료와
일치한다.** 경로가 DEGRADED → RUNNING 으로 돌아오는 동안(약 1.9초) WireGuard 가 자기
**staged 큐**(리눅스 구현: 피어당 최대 128패킷, 핸드셰이크 완료 시 일괄 방출)에 담아둔 것이다.
multi-fec 의 큐가 아니므로 multi-fec 의 TTL 로는 줄일 수 없다.

이는 09-09 SPOF 시험의 **"복구 자동 2.8초"** 와도 정합적이다 — 그 2.8초 역시 경로 복귀와
핸드셰이크 재수립 시간이었다.

### 9-나. 그럼 v1.3.2 는 무엇인가

**측정 가능한 효과가 없는, 정합성 수정이다.** 서버 큐는 여전히 "성공 경로에서 나이를 보지
않는" 상태였고 그것은 클라이언트와 비대칭이다 — 경로 단절이 아니라 **window 고갈로 큐가
밀리는 경우**(고부하)에는 서버가 묵은 하향을 낼 수 있다. 그 시나리오는 이번에 재현하지
않았다. 회귀는 전부 통과했고(유닛 10/10·7/7·11/11, 라우팅 9/9, 다운스트림 24/24, 세션 상한
4/4, CLI 90/90, 경고 0) 와이어는 무변경이다.

**서비스 권장은 여전히 v1.3.1 이다** — v1.3.2 는 30분 누수 소크를 아직 돌리지 않았다.

### 9-다. 방법 교훈

**"한 시점에 몰려 도착 + RTT 가 프로브 간격씩 감소"는 큐가 하나 있다는 신호일 뿐, 어느
계층의 큐인지는 말해주지 않는다.** §3-나 는 그 서명만 보고 multi-fec 서버 큐로 단정했다.
송신 시각 귀속(`송신 = 수신 − RTT`)까지 했는데도 **터널 자신이 큐를 갖는다는 가능성**을
후보에서 빠뜨린 것이 오류였다. 계층별로 같은 서명을 내는 큐를 먼저 열거하고, 각 계층의
상태(여기서는 `wg latest-handshakes`)를 함께 샘플링해야 한다.
