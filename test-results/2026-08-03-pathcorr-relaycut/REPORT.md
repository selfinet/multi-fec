# 경로 상관도 측정 · 릴레이 단절 시도 · gw 과부하 사고 (2026-08-03)

**한 줄 요약**: 경로 상관도는 완주해 **두 경로가 독립**임을 30만 페어로 확인했다(φ = −0.00017).
릴레이 단절 테스트는 하네스 결함으로 무효. 측정 중 **gw `ens18` 이 800 Mbps 를 넘어 사용자가
중단**시켰고, 원인을 추적해 **터널이 자기 하부 전송망을 삼키는 라우팅 루프**를 c·s 양쪽에서
찾아 제거했다.

| 항목 | 결과 |
|---|---|
| 경로 상관도 | ✅ 완료 — 독립. `p1 × p2` 예측 유효 |
| 릴레이 단절(duplicate) | ❌ 무효 — 하네스 `pkill` 자기자신 매치로 에코 미기동 |
| 릴레이 단절(aggregate) | 미착수 |
| gw 800 Mbps 사고 | 원인 구조 규명, 라우팅 수정 완료. **인과는 미확정** |
| 라우팅 루프 제거 | ✅ c·s 양쪽 (런타임 + netplan + WG hook) |
| 설정 고정 | ✅ c·s 부팅 자동기동(원래 `disabled` 였음) + r 의 `.85` DHCP→static |

## 1. 경로 상관도 — 두 경로는 독립이다

### 1-1. 왜 재야 했나

`duplicate` 의 종단 손실을 `p = p1 × p2` 로 예측하는 것은 **두 경로의 손실이 독립일 때만**
성립한다. 완전 상관이면 `p = p1` 이라 필요한 FEC 강도가 전혀 달라진다. `-f` 결정 전체가
이 값에 달려 있는데 한 번도 측정한 적이 없었다.

### 1-2. 방법

두 경로에 **같은 시퀀스를 연속 두 번** 쏘고, 종단에서 경로별 도착 여부를 대조해 2×2 분할표를
만든다. 두 사본이 같은 순간의 네트워크 상태를 겪어야 하므로 사이에 `sleep` 을 넣지 않는다.

```
c: pc_send.py ─┬─ .85:40001 ─┐
               └─ .86:40001 ─┤  r: pc_fwd.py (IP별 소켓 2개)
                             └──── 192.168.200.254:40000 ──► s: pc_sink.py
```

파라미터: **500 pps × 2경로 × 1200 B × 600 초 = 300,000 페어** (경로당 4.8 Mbps).

**설계상 반드시 필요했던 것 하나** — netem u32 필터가 dst IP 뿐 아니라 **`dport 443` 까지
매치한다**(`match 000001bb/0000ffff at 20`). 프로브를 40001 로 쏘면 band 3(무임피어먼트)로
빠져 **netem 을 전혀 안 받는다.** `pc_setup.sh` 로 `pref 2` 필터를 임시 추가해 실제 경로와
같은 netem 인스턴스(1:1 / 1:2)에 태우고, 끝나고 `pref 2` 통째로 지웠다. 기존 `pref 1` 은
건드리지 않았다.

### 1-3. 하네스 검증

| 단계 | 결과 | 의미 |
|---|---|---|
| 필터 없이 2,000 페어 | **2000/2000 양쪽 도착**, 중복 0 | **`r→s` 공유 구간 손실 0** |
| 필터 적용 4,000 페어 | p_A 4.88%, p_B 2.00% | netem 설정값(5%/2%)과 일치 |

첫 줄이 중요하다. 릴레이 호스트와 gw 를 지나는 **공유 구간이 무손실**임을 확인했고,
이것이 상관도가 0으로 나온 직접적인 이유다.

### 1-4. 결과 (N = 300,000)

```
                 B 도착      B 손실
  A 도착         279,283       5,647
  A 손실          14,773         297   ← n00 = 양쪽 동시 손실
```

| 지표 | 값 |
|---|---|
| P(A 손실) | 5.0233% |
| P(B 손실) | 1.9813% |
| **P(양쪽 손실) 실측** | **0.09900%** (297건, 95%CI 0.0884~0.1109%) |
| P(양쪽 손실) 독립가정 | 0.09953% (298.6건 기대) |
| 실측 / 독립기대 | **0.99 배** |
| **φ 상관계수** | **−0.00017** |
| 공유구간 손실 추정 | 0.00000% |
| 중복 수신 / 형식오류 | 0 / 0 |

**판정: 독립과 구분되지 않는다. `p1 × p2` 예측이 유효하다.**

### 1-5. 해석의 한계 — 이 수치를 실환경에 옮기지 말 것

현 테스트망의 손실은 **netem 이 `c→r` 구간에 경로별로 독립 주입**한 것이다. 독립이 나오는 게
구조상 당연하다. 이 결과가 말하는 것은 **"현 테스트망에 숨은 공유 장애요소가 없다"** 이지,
실제 POP 두 곳이 독립이라는 근거가 아니다. 실환경은 해저케이블·IX·상위 ISP 를 공유할 수 있어
별도 측정이 필요하다.

## 2. 릴레이 단절 테스트 — 무효 (하네스 결함)

WG 터널 위에서 왕복 프로브를 흘리며 `relay@b` 를 죽였다 살리는 설계였다
(0s 시작 → 40s 절단 → 100s 복구 → 180s 종료, 100 ms 버킷으로 `sent`/`recv`/`rtt` 기록).

1차 시도가 `sent=36000 recv=0`, **손실 100%** 로 나왔다. 제품 결함이 아니라 `rc_run.sh` 버그다.

```bash
pkill -f 'rc_echo[.]py'      # ← 이 명령을 실행하는 원격 셸 자신의 커맨드라인에
                             #    'python3 /tmp/rc_echo.py' 가 들어 있어 자기를 죽인다
```

로그의 `[echo] procs=0` 이 그 증거다. **같은 함정에 이 세션에서 세 번 걸렸다** — 최초 sink
기동, 이 에코 기동, 그리고 정리 단계. 브래킷 패턴(`'[r]c_echo'`)으로 해결된다.

재개 전 고쳐야 할 것:
1. `rc_run.sh` 의 `pkill` 을 브래킷 패턴으로
2. **규칙 변경 반영** — 프로브 목적지를 WG IP 로 (§6)
3. 부하 전 `mf_gwguard.sh watch` 기동

## 3. gw 800 Mbps 사고

### 3-1. 경위

측정 중 사용자가 **gw `ens18` 이 800 Mbps 를 넘었다**며 중단시켰다. 내 사전 계산은 gw 통과분
편도 9.6 Mbps 였다 — **80배 어긋났다.**

### 3-2. 절차 실패 (측정자 과실)

`mf_gwguard.sh` 를 **띄우지 않았다.** 손계산으로 "여유롭다" 판단하고 워치독 없이 10분 런을
돌렸다. 기존 문서에 이미 "상수 환산계수를 쓰지 말 것", "기저는 고정이 아니며 타 장비 때문에
200 Mbps 까지 간 적 있음", "`watch` 로 자동 중단" 이 모두 적혀 있었다.

가드가 있었으면 초과 즉시 잡아 "내 트래픽이 아니다"를 그 자리에서 확인할 수 있었고,
아래의 사후 추적도 필요 없었다.

### 3-3. 수집한 증거

| # | 증거 | 판단 |
|---|---|---|
| ① | 클라이언트 `--report` 누적 카운터: 14:09:09 tx=1,174,435 → 14:14:39 tx=1,181,185 = **20.5 pps** | multi-fec 은 **유휴**. 800 Mbps 는 여기를 통과하지 않았다 |
| ② | 프로브 gw 통과분 = 9.6 Mbps, 헤어핀 2회 계상 → **약 19 Mbps** | 800 의 2.4% |
| ③ | 사후 전 인터페이스 5초 델타: c 109/100, r 251/245, s 126/124 kbps | 진행 중인 루프 없음 |
| ④ | `sysstat` c·s 설치돼 있으나 **inactive**, 모니터링 에이전트 없음 | **이력 부재 — 시간대 재구성 불가** |

**인과는 확정하지 못했다.** gw 데이터가 있어야 하고 gw 는 조회 금지 범위다.

### 3-4. 그러나 — 800 Mbps 를 만들 수 있는 구조를 찾았다

WireGuard PostUp 이 **터널을 실어 나르는 경로를 터널 안으로** 보내고 있었다.

```bash
# c: /etc/wireguard/routes/postup-starlink-fec
ip route add 192.168.200.0/24 dev starlink-fec via 10.9.10.1 metric 10
#   └ s 의 실제 IP 192.168.200.254 포함 = 릴레이의 upstream 목적지

# s: /etc/wireguard/routes/postup-starlink-fec
ip route add 192.168.100.0/24 dev starlink-fec via 10.9.10.2 metric 10
#   └ 릴레이 192.168.100.85 / .86 포함 = 클라이언트 path 목적지
```

`starlink-fec` 의 엔드포인트는 `127.0.0.1:51821` = multi-fec 자신이다.

```
s 서버가 192.168.100.85 로 송신 → 라우트가 터널로 → WG 캡슐화 → 127.0.0.1:51821
  → multi-fec 서버 → FEC + duplicate ×2 → 목적지 192.168.100.85 → 다시 터널로 …
```

**한 바퀴마다 2배.** `duplicate` 가 배수기다. 이것이 내가 메우지 못하던 80배 격차의
유일한 후보다. 다만 **발동했다는 직접 증거는 없다** — 발동했다면 ①의 카운터가 폭증했어야 한다.

트리거 후보: `pc_fwd.py` 가 소스 `192.168.100.85` 로 s 에 보냈고, **sink 가 안 뜬 채로 쏜
구간이 실제로 있었다**(첫 스모크에서 `pkill` 이 sink 를 죽인 걸 모르고 200 pps × 10초).
그때 s 가 그 소스로 낸 ICMP port unreachable 이 위 라우트에 걸린다.

### 3-5. 대안 가설 — 배제하지 못했다

`c` 는 테스트 클라이언트가 아니라 **운영 라우터**다: `ip_forward=1`, LAN 2개
(`192.168.50.0/24`, `enp3s0 192.168.1.0/24`), `default via 192.168.100.1`(gw),
누적 `enp2s0` TX **2.16 TB / 28억 패킷**, starlink-fec 로 향하는 프리픽스 48개.

이 LAN→인터넷 트래픽은 gw `ens18` 을 지나면서 **multi-fec 카운터에도, 내 측정에도 안 잡힌다.**
세그먼트에서 800 Mbps 를 낼 체급은 여기뿐이다. 선례도 있다 — 2026-08-02 에 gw 가 200 Mbps 까지
갔는데 우리 몫은 45 뿐이었다.

## 4. 라우팅 수정 (적용 완료)

`/32` 예외가 아니라 **`/24` 를 통째로 gw 경유로** 바꿨다. c·r·s 의 default 가 gw 이고 gw 가
두 서브넷에 다리를 걸친 라우터라 **터널로 우회할 이유가 애초에 없었다.**

```bash
# s
ip route replace 192.168.100.0/24 via 192.168.200.1 dev ens18
# c
ip route replace 192.168.200.0/24 via 192.168.100.1 dev enp2s0
```

> **⚠️ s 는 `ip route del` 만 하면 안 된다.** s 의 default 는 gw 가 아니라 공인 `ens19` 라,
> 지우기만 하면 `192.168.100.0/24` 가 인터넷으로 샌다. 반드시 `replace` 로 gw 경유를 먼저
> 넣을 것. (c 는 default 가 gw 라 해당 없음)

**영구화 위치가 중요하다.** gw 경유 라우트는 **netplan** 에 넣었다. WG PostUp 에 넣으면 WG 가
내려갈 때 PostDown 이 지워 서버가 릴레이에 못 닿는다 — **multi-fec 은 WG 와 독립**이다.

| 호스트 | 파일 | 변경 |
|---|---|---|
| s | 런타임 | `replace` 후 터널 라우트 삭제 |
| s | `netplan/00-installer-config.yaml` | `routes:` 절에 `.100.0/24 via .200.1` |
| s | `wireguard/routes/postup-starlink-fec` | 루프 유발 줄 제거 + 사유 주석 |
| c | 런타임 | `replace` 후 터널 라우트 삭제 |
| c | `netplan/00-installer-config.yaml` | `routes:` 절에 `.200.0/24 via .100.1` |
| c | `postup`/`postdown-starlink-fec` | 루프 유발 줄 제거(양쪽) + 사유 주석 |

백업: `*.bak-20260803`, `/tmp/route-backup-*.bin`.
`netplan apply` 는 **미실행** — 런타임이 이미 올바르고 운영 호스트 단절 위험이 있어 보류.
`netplan generate` 로 문법만 검증(양쪽 OK), 다음 부팅에 적용된다.

### 검증 — 12개 조합 전수

```
[c] → r .85/.86  enp2s0 온링크        [r] → c .141    ens18 온링크
[c] → s .254     via 192.168.100.1    [r] → s .254    via 192.168.100.1
[s] → c .141     via 192.168.200.1    [s] → r .85/.86 via 192.168.200.1
```

| 항목 | 결과 |
|---|---|
| c → s `.254` | 0% 손실, **RTT 1.30 ms** (터널 경유였다면 55 ms) |
| s → 릴레이 `.85`/`.86` | 0% 손실, **RTT 1.00 ms** |
| WG 터널 c↔s | 3/3, RTT 54.7 ms — 변화 없음 |
| 경로 상태 | path[0]·path[1] 모두 RUNNING |
| 서비스 | c client / r relay·relay@b / s server 전부 active |

터널에 남긴 것: c 의 인터넷 프리픽스 48개(전부 공인), s 의 `192.168.50.0/24`
(c 뒤 LAN, gw 에 경로가 없어 터널이 유일한 경로). 터널 자신의 `10.9.9.0/24`·`10.9.10.0/24`.

## 5. 설정 고정 (사용자 지시)

라우팅을 고쳐도 **재부팅을 견디지 못하면 의미가 없다.** 현재 구성을 기준선으로 고정하면서
두 가지 구멍을 찾았다.

### 5-1. c·s 의 서비스가 부팅 시 안 올라왔다

```
변경 전   c: multi-fec-client[active/disabled]  wg-quick@starlink-fec[active/disabled]
          s: multi-fec-server[active/disabled]  wg-quick@starlink-fec[active/disabled]
          r: multi-fec-relay[active/enabled]    multi-fec-relay@b[active/enabled]
```

**c·s 는 수동 기동 상태로만 떠 있었다** — 재부팅하면 터널 체인이 안 올라온다. `crontab`·
`rc.local` 등 다른 기동 경로도 없음을 확인했다. `starlink-fec` 은 테스트 전용이 아니라 c 가
인터넷 프리픽스 48개를 실어 보내는 실사용 터널이므로 자동기동이 맞다고 판단해 `enable` 했다
(`systemctl enable` 은 실행 중 서비스를 건드리지 않는다).

라우팅만 고쳐놓고 이걸 놓쳤다면 다음 재부팅에 조용히 끊겼을 것이다.

> `wg-quick@starlink-xdn`(직결)은 c=enabled / s=disabled 로 **비대칭**이다. 측정에 쓰지 않는
> 터널이라 손대지 않았다.

### 5-2. r 의 `.85` 가 DHCP 산물이었다

```
변경 전   ens18: 192.168.100.85/24  ← DHCP (LIFETIME 7200, 서버 = gw)
                 192.168.100.86/24  ← static
          default via 192.168.100.1  proto dhcp  metric 100
```

**secondary 가 primary 보다 안정적인 상태였다.** 위험은 둘이다:

| 시나리오 | DHCP 일 때 | static 전환 후 |
|---|---|---|
| gw 가 `.85` 를 다른 장비에 배정 | 릴레이 `LISTEN=192.168.100.85:443` **바인딩 실패 → 기동 거부 → path[0] 소실** | 영향 없음 |
| DHCP 서버 무응답 | **default route 소멸 → r→s 불가 → 두 경로 동시 사망** | 영향 없음 |

부팅 후 **21주간 리스 갱신 약 3,650회 동안 `.85` 가 유지**돼 왔다 — gw 에 MAC 예약이 걸려
있을 가능성이 높지만 gw 조회는 금지 범위라 확인하지 못했다. 다만 위 표대로 multi-fec 관점에서는
static 이 두 경우 모두 낫기 때문에 전환했다.

**전환 전 검토에서 걸러낸 3가지:**

1. **`dhcp4: false` 명시 필요.** netplan 은 파일을 **키 단위로 병합**하므로 이 줄이 없으면
   `50-cloud-init.yaml` 의 `dhcp4: true` 가 살아남는다. 기존 `99-relay-secondary.yaml` 이
   `addresses` 만 얹어 DHCP 와 공존했던 것이 그 증거다.
2. **DHCP 가 주던 것 전수 대체.** 리스에 있던 것은 주소·넷마스크·`ROUTER`·`DNS` 네 가지 →
   `addresses` / `routes: default` / `nameservers` 로 덮었다.
3. **MTU.** 생성 설정에 `UseMTU=true` 가 있어 DHCP 가 MTU 를 줄 수 있었다. 리스를 확인해
   **MTU 옵션이 없음**을 보고 진행했다(1500 유지). 있었다면 static 전환이 `--mtu 1350`
   전제를 흔들었을 것이다.

생성 결과를 diff 로 등가 확인한 뒤 적용했다:

```diff
 [Network]
-DHCP=ipv4
 LinkLocalAddressing=ipv6
+Address=192.168.100.85/24
 Address=192.168.100.86/24
+DNS=8.8.8.8
-[DHCP]
-RouteMetric=100
-UseMTU=true
+[Route]
+Destination=0.0.0.0/0
+Gateway=192.168.100.1
```

DHCP 항목이 **같은 값의 static 항목으로 1:1 대체**된다. 사라지는 `8.8.8.8 via .1`·
`.1 scope link` 호스트 라우트는 default 와 온링크 `/24` 가 덮으므로 무해하다.

### 5-3. ⚠️ r 에 `netplan apply` 하는 절차

**r 은 `ens18` 로만 접근 가능하고 콘솔이 없다** — 설정이 틀리면 원격 복구가 불가능하고 릴레이
2개가 동시에 죽는다. 안전망을 걸고 진행했다:

```bash
# ③ 180초 후 자동 원복 예약 (SSH 끊겨도 살아남는 transient unit)
sudo systemd-run --unit=netplan-revert --on-active=180 /bin/bash -c \
  'cp <백업> /etc/netplan/99-relay-secondary.yaml && netplan apply'
# ④ apply 도 detached 로 (SSH 끊겨도 완주)
sudo systemd-run --unit=netplan-apply-now /usr/sbin/netplan apply
# ⑤ 재접속·주소·라우팅·DNS·MTU·릴레이·s도달 확인 → ⑥ 타이머 stop
```

`netplan try` 는 TTY 확인이 필요해 **비대화형에서는 항상 되돌아가므로 쓸 수 없다.**

### 5-4. 고정된 기준선

| 호스트 | 주소 | 라우팅 | 부팅 자동기동 |
|---|---|---|---|
| c | `.141/24` + `.50.1/24` static | default → gw, `.200.0/24` → gw | client, wg-fec, mf-netem |
| r | `.85/24` + `.86/24` **static** | default → gw (`proto static`) | relay, relay@b, mf-netem |
| s | `.200.254/24` static | `.100.0/24` → gw | server, wg-fec |

**기준값**: WG 터널 RTT 54.3~54.9 ms, s→릴레이 1.00 ms, c→s `.254` 1.30 ms,
유휴 시 s ens18 RX/TX 약 120/210 kbps. r 의 DHCP 리스 파일 **0개**.

`netplan apply` 는 c·s 에서는 **미실행**(런타임이 이미 올바르고 운영 호스트 단절 위험 회피),
r 에서만 안전망을 걸고 실행했다. 생성물에 `[Route]` 가 들어간 것을 확인했으므로 c·s 도
다음 부팅에 적용된다.

### 5-5. 삭제한 잔재 (사용자 승인)

- **루프 라우트 담긴 백업** — c·s 의 netplan/postup/postdown `*.bak-20260803`,
  `/tmp/route-backup-*.bin`. **복원하면 루프가 되살아난다.** 정상 설정은 라이브 파일에 있고
  c 의 프리픽스 48개도 온전하다.
- **c `client.conf` 의 `DEST_C=192.168.100.85:8443`** — 가리키는 릴레이가 없어진 잔재
  (미사용 변수라 무해했음). unit 은 `${DEST_A}`/`${DEST_B}` 만 참조.
- **하네스 스크립트** — c·r·s 의 `/tmp/pc_*`, `/tmp/rc_*`. 리포에 사본 있음(§7).
- **s `/etc/rc.local`** — 실행권한 없고 `rc-local` 도 inactive 인 완전 사문. 삭제 전 확인:
  참조 프로세스 0개, 넣는다는 라우트 4개 전부 부재. multi-fec 무관한 타 서비스 중계 설정이
  들어 있었고 **내용은 복원 불가**다.

## 6. 확정된 테스트 규칙 (사용자 지시)

**규칙 1 — 트래픽 테스트는 WG IP 사이에서만.**

```
c 10.9.10.2  ↔  s 10.9.10.1     (starlink-fec, multi-fec 경유)
```

c/r/s 의 실제 IP 로 직접 프로브를 쏘지 않는다. 이번 상관도 측정이 릴레이·서버 실제 IP 로
raw UDP 를 쏴서 하부 전송망을 건드렸고 그게 §3-4 의 루프 조건에 노출됐다.
**`starlink-xdn`(c 10.9.9.2 / s 10.9.9.1)은 직결이라 multi-fec 을 안 탄다 — 측정 금지.**

> **대가**: 경로별 상관도는 이 방식으로 측정할 수 없다. duplicate 두 사본이 dedup 되어 앱
> 계층에서 경로를 구분할 수 없기 때문이다. 재측정이 필요하면 **서버에 경로별 수신 카운터를
> 노출**시키는 쪽으로 설계해야 한다(릴레이 우회 금지).

**규칙 2 — c/r/s 의 IP 는 절대 터널로 라우팅하지 않는다.** 변경 후 12개 조합 전수 확인.

**규칙 0 (기존)** — 부하 시작 **전에** `mf_gwguard.sh watch` 를 띄운다. 손계산 금지.
