# 측정 — `s` 리슨 이전 후 첫 부하 시험 · 새 부하 지표 검증 (2026-08-06)

**대상**: 테스트망 (c·r·s) · 배포 바이너리 **v1.0.9** · 리포 `dev` v1.2.0
**목적**: ① `s` 리슨을 `192.168.100.84` 로 옮긴 뒤 데이터 경로가 정상 동작하는지
② 새로 만든 부하 지표(`mf_gwguard.sh` 재작성)가 실측과 맞는지 ③ 시험 트래픽이
`192.168.100.0/24` 밖으로 새지 않는지

---

## 0. 요약

| 항목 | 결과 |
|---|---|
| 앱 손실 (양방향, netem 5%/2% 하에서) | **0 / 24,039 · 0 / 24,040 (0.000%)** |
| 앱 실효 | 각 방향 **4.00 Mbps** (10초 구간 6개 전부) |
| 용량 모델 예측 vs 실측 (각 방향 4 Mbps) | 예측 22% vs **23.2% / 28.7%** — 이 한 점에서만 15~18% 낙관적 |
| 가드 초과·트립 | 4 Mbps 두 런 **0건 / 0건** · 계단 전체 3건 / **0건** (붕괴를 못 잡았다 → §9-다) |
| 회선 증폭 (앱 대비) | **2.75배** |
| WG RTT | 부하 중 **53.21 ms** (유휴 기준 54.08) — 열화 없음 |
| 경로 상태 | `path[0]`·`path[1]` 전 구간 **RUNNING**. LOSSY·DEGRADED 0회 |
| 시험 트래픽 격리 | **전량 `192.168.100.0/24`**. 공인 인터페이스 기여 0.024% (ISP 브로드캐스트 편차) |
| **실용 한계 (계단, §9)** | **앱 각 방향 22 Mbps** — 기존 문서 8 Mbps 의 **2.75배**. 옛 한계는 gw 바운드였다 |
| **붕괴점** | 각 방향 34 Mbps — 최고1코어 85.7%, 실효 미달, 손실 14% |
| **용량 모델 (§10)** | 12 Mbps 근방에서만 유효. R=44 에서 예측 118% vs 실측 57% (**2.1배 과대**) |

**결론**: 온링크 전환 후 첫 부하 시험 통과. 새 지표는 예측·실측이 맞아 사용 가능하다.
**gw 를 경로에서 뺀 효과가 실용 한계 2.75배로 나타났다** — 옛 8 Mbps 한계는 CPU 가 아니라
gw 바운드였다(§9). 다만 시험 준비 중 **가드가 원격 부하를 못 멈추는 결함**을 발견해
수정했고(§6), 아직 원인을 모르는 계측 이상 2건이 남았다(§5). 가드 임계도 느슨하다(§9-다).

## 1. 구성

```
c 192.168.100.141 ──┬─ path[0] → r 192.168.100.85:443 ─┐
                    └─ path[1] → r 192.168.100.86:443 ─┴→ s 192.168.100.84:443
                       (netem 25ms/5%)   (netem 30ms/2%)      임피어먼트 없음
```

전 구간 온링크 — gw 미통과(2026-08-05 이전 완료, `CLAUDE.md` §26 후속).

| | 설정 |
|---|---|
| multi-fec | `duplicate` · `--mode 1` · `-f 5:1,20:4` · `--fec-timeout 10` · `--mtu 1350` |
| | `--decode-buf 2000` · `--queue-len 500` · `--sock-buf 4096` · `--auth-interval 60` |
| netem | `c↔r` 구간에만. path[0] 편도 25ms/5%, path[1] 편도 30ms/2% |
| 부하 | `iperf3 -u -b 4M --bidir`, 앱 각 방향 4 Mbps |

**부하 도구 바인딩** (규칙 1 — 트래픽은 WG IP 사이에서만):

```bash
# s
iperf3 -s -B 10.9.10.1 -p 5201 -D          # 터널 IP 에 명시 바인딩
# c
iperf3 -c 10.9.10.1 -p 5201 -u -b 4M --bidir -t 60 -i 10
  → local 10.9.10.2 port 47046 connected to 10.9.10.1 port 5201
```

`-B 10.9.10.1` 이 핵심 안전장치다. 실제 IP(`.141`→`.84`)로 쐈다면 multi-fec 을 타지 않고,
`starlink-xdn`(10.9.9.x)도 직결이라 마찬가지로 측정이 조용히 무의미해진다.

## 2. 앱 계층 결과 (iperf3, 60초)

| 방향 | 전송량 | 실효 | 지터 | 손실 |
|---|---|---|---|---|
| c → s (TX-C) | 28.6 MB | 4.00 Mbps | 0.861 ms | **0 / 24,039 (0%)** |
| s → c (RX-C) | 28.6 MB | 4.00 Mbps | 0.240 ms | **0 / 24,040 (0%)** |

10초 구간 6개 모두 정확히 4.00 Mbps · 0% 손실.

**netem 이 path[0] 5% / path[1] 2% 를 떨어뜨리는데 앱 손실이 0이다** — `duplicate` 두 사본과
FEC 가 전부 복구했다. 경로 독립성(2026-08-03 측정, φ = −0.00017)에서 두 경로 동시 손실은
`0.05 × 0.02 = 0.1%` 이고 그 잔여를 FEC 가 덮는 구조와 일치한다.

`s → c` 방향에 **out-of-order 887개**(24,040 중 3.7%). 경로 지연차 5 ms(25 vs 30) × 약 370 pps
≈ 2패킷 재정렬로 설명되는 범위다. UDP 라 앱에 영향 없음.

## 3. 새 부하 지표 검증

### 3-가. 사전 판정 (`budget`)

```
$ mf_gwguard.sh budget 8 1          # 1세션 × 양방향 8 Mbps
  ① 총량  비용 0.87 / 예산 2.00 논리CPU  → c 전체 busy 약 22%
  ② 개별  R 8.00 / 15.9 Mbps
  ③ NIC   ΣR 8.00 / 31.25 Mbps 양방향
  ✓ 안전 (총량 여유 1.13 논리CPU)
```

### 3-나. 실측 (`sample`)

| | 기저 | t+12s | t+30s | 부하 후 |
|---|---|---|---|---|
| **c 전체 CPU** | 1.2% | **23.2%** | **28.7%** | 1.0% |
| c 최고 1코어 | 2.0% | 35.4% | 39.4% | 2.0% |
| c `enp2s0` | 0.23 | 21.93 | 21.83 | 0.22 Mbps |
| r `ens18` | 0.39 | 44.38 | 44.66 | 0.46 |
| s `ens18` | 0.27 | 22.27 | 22.47 | 0.29 |

**예측 22% vs 실측 23.2%(+1.2p) / 28.7%(+6.7p).** 평균 26.0% 로 모델이 **15~18% 낙관적**이다.
용량 모델 메모가 경고한 방향("미확정 요소가 전부 불리한 방향 — 스케줄링·FEC flush 버스트·캐시
경합")과 일치한다. 예측용으로는 충분하고, 여유를 20% 정도 두면 된다.

`r ens18` 이 `c`·`s` 의 2배인 것은 **r 이 중간 홉**이라서다 — 모든 패킷이 r 의 NIC 를 두 번
지난다(c 에서 들어오고 s 로 나감). 지표를 읽을 때 이 배수를 기억할 것.

**가드는 두 런 모두 초과 0건 · 트립 0건.** 최고1코어가 39.4% 로 임계 90% 까지 여유가 크다.

> 이 절의 "모델이 15\~18% 낙관적" 은 **각 방향 4 Mbps 한 점의 결론**이다. §10 에서 보듯
> 고배율에서는 반대로 **2.1배 과대**가 된다 — 비용이 sublinear 라 한 점의 오차 방향을
> 외삽하면 안 된다. 임계값 적절성도 §9-다 에서 뒤집힌다(붕괴를 못 잡았다).

### 3-다. 지표 산식 대조 (네트워크 트래픽 없이)

```
c 에서 1코어 점유  →  전체 27.1% / 최고1코어 100.0%      (4논리 기준 25% + 기저)
c 에서 2코어 점유  →  전체 51.0% / 최고1코어 100.0%
유휴              →  전체  2.9% / 최고1코어   6.8%
```

산식이 정확하다. `busy = user+nice+system+irq+softirq+steal`, `idle`·`iowait` 제외.

## 4. 증폭과 트래픽 격리

### 4-가. 계층별 실측 (12초 런, 10초 창, 전 인터페이스)

```
  c  enp2s0        RX  11.052  TX  11.025 Mbps   ← 192.168.100.0/24
  c  starlink-fec  RX   4.206  TX   4.204        ← WG (논리 인터페이스)
  r  ens18         RX  22.374  TX  21.988        ← 192.168.100.0/24  (중간 홉)
  s  ens18         RX  10.981  TX  11.372        ← 192.168.100.0/24
  s  starlink-fec  RX   4.205  TX   4.205        ← WG (논리 인터페이스)
  s  ens19         RX   0.069  TX   0.019        ← 공인 (§4-다)
```

`c enp3s0`, `s ens20` 은 임계(0.01 Mbps) 미달. 같은 런의 앱 결과는 각 방향 3.98 Mbps · 0% 손실.

### 4-나. 증폭 분해 (편도 기준)

```
앱 4.00 Mbps  →  WG 4.205  →  회선 11.03 Mbps

  회선 / WG = 2.623
    duplicate  2.000   두 경로에 같은 패킷
    FEC        1.228   서버 report 실측: original 31.64 MB → fec 38.86 MB
    obfs·헤더  1.068   패딩 + mud 8B + IP/UDP
             ─────────
             2.623 ✓
```

앱 대비로는 **2.75배**. 문서의 실측 범위(2.66~3.02배, `-f 5:1,20:4`/t10)와 일치한다.

**FEC 증폭 1.228 의 근거** — 서버 report 부하 전후 델타:
original 24,077 pkt / 31,639,296 B, fec 29,359 pkt / 38,857,398 B → 38,857,398 / 31,639,296 = **1.2281**

### 4-다. 트래픽 격리 — 시험 데이터는 전량 테스트망 안

경로가 **관측 결과가 아니라 구조적으로 강제**된다. 각 계층에 출구가 하나뿐이다:

```
iperf3 목적지 = 10.9.10.1 = s 자신의 터널 IP     → s 에서 종료. 포워딩 판단 자체가 없다
WG 의 유일한 출구 = Endpoint 127.0.0.1:51821     → multi-fec 하나. 대안 경로 없음
multi-fec 의 유일한 출구 = --path .85:443 / .86:443 → 192.168.100.0/24 온링크
```

`starlink-fec` 의 4.2 Mbps 는 **추가 회선 트래픽이 아니다.** 가상 인터페이스라 자체 와이어가
없고 WG 가 캡슐화해 루프백으로 multi-fec 에 넘긴다 — 같은 데이터를 계층별로 두 번 센 것이다.

**`s ens19`(공인)에 있던 것의 정체** — 수동 캡처 12패킷 전수:

```
ARP, Request who-has 59.15.120.80 tell 59.15.120.126      ← ISP 세그먼트 ARP
ARP, Request who-has 218.154.2.194 tell 218.154.2.254
IP 218.154.1.93 > 224.0.0.18: VRRPv2, vrid 55             ← ISP 라우터 이중화
... 12개 전부 ARP / VRRP. 시험 트래픽 0
```

- **RX 44~69 kbps** = ISP 브로드캐스트. 공인 IP 를 꽂고 있으면 상시 들어온다(유휴에도 동일).
- **TX 19 kbps** = **가드 자신의 ssh 폴링.** `sv1` 은 `s` 에 공인 `218.154.1.134:2255` 로 붙고
  (`c`·`r` 은 `sv1-gw` 터널), 가드가 2초마다 세 호스트에 ssh 를 연다 — 10초에 s 로 5회,
  핸드셰이크 약 4 KB씩 ≈ 16 kbps. 계산이 맞는다.

즉 **감시 경로가 외부를 지난다.** 측정을 오염시키지는 않지만(시험 트래픽은 `ens18`) 시험
절차가 만드는 외부 트래픽이므로 기록해 둔다. 줄이려면 `GW_INTERVAL` 을 늘린다.

**60초 전 구간 누적으로 재확인** (`ifbytes.sh`) — 10초 창이 놓칠 수 있는 순간 유출까지 잡기
위해, **가드를 양 구간에 동일하게 켜두고** 유휴 60초와 부하 60초의 누적 바이트를 비교했다.
가드 자신의 ssh 폴링이 양쪽에 들어가 상쇄되므로 차이가 곧 부하의 기여분이다.

| 인터페이스 | RX 기여 | TX 기여 | 대역 |
|---|---|---|---|
| `c enp2s0` | **81.72 MB** | **81.90 MB** | `192.168.100.0/24` |
| `c starlink-fec` | 31.57 | 31.54 | WG (논리) |
| `r ens18` | **166.18** | **163.15** | `192.168.100.0/24` (중간 홉) |
| `s ens18` | **81.67** | **84.51** | `192.168.100.0/24` |
| `s starlink-fec` | 31.54 | 31.57 | WG (논리) |
| **`s ens19`** (공인) | **0.02** | **−0.00** | **사실상 0** |
| `s ens20` (공인) | 0.00 | 0.00 | 0 |
| `c enp3s0` | 0.00 | −0.00 | 0 |

공인 인터페이스 기여가 **RX 20 KB / TX 0**이다. 같은 60초에 테스트망이 81.7 MB 를 날랐으니
비율로 **0.024%** 이고, 그 20 KB 조차 ISP 브로드캐스트 유입량의 창간 편차다. **TX 는 아예
움직이지 않았다**(0.12 → 0.12 MB) — 앞서 19 kbps 를 가드 ssh 로 귀속한 판단이 확인된다.

총량 수지도 맞는다: 앱 57.2 MB → WG 63.1 (×1.103, UDP/IP 헤더) → 회선 163.6 (×2.593),
`r` 은 그 2배(329.3, 중간 홉), `s` 는 `c` 와 동급(166.2). **설명되지 않는 트래픽이 없다.**

## 5. 미해결 계측 이상 2건

### 5-가. 클라이언트 report 의 `rtt` 단위

```
[client] path[0] RUNNING rtt=26us jit=0us loss=13% rate=36.8Mbps
[client] path[1] RUNNING rtt=31us jit=0us loss=0%  rate=17.1Mbps
```

**값 26 / 31 이 netem 편도값 25 / 30 ms 와 숫자가 정확히 맞는데 단위 표기가 µs 다.**
로그 단위 버그인지 다른 의미인지 확인하지 않았다. RTT 는 경로 선택에 쓰이지 않으므로
(§4 — `mud_path_update()` 에 RTT 분기가 없다) 동작 영향은 없어 보인다.

### 5-나. 보고 손실률이 netem 과 맞지 않는다

| | netem 설정 | 보고값 |
|---|---|---|
| path[0] | 편도 5% | **7 ~ 14%** |
| path[1] | 편도 2% | **0 ~ 1%** |

path[0] 의 과대는 §24 의 in-flight 팽창으로 설명된다(probe 도착 시점의 미도달분이 손실로
계상, 1초 창·RTT 50ms 에서 3~4% 수준). **그러나 path[1] 이 0% 로 나오는 것은 반대 방향이라
설명되지 않는다.** 두 경로 모두 LOSSY 임계(78.4%)에서 멀어 이번 시험에 영향은 없었다.

두 건 모두 계측·표시 문제로 보이고 데이터 경로 동작에는 영향이 관측되지 않았다.

## 6. 시험 준비 중 수정한 결함 — 가드가 원격 부하를 못 멈췄다

이 시험을 위해 `mf_gwguard.sh` 를 재작성하다 발견했다. **가드가 부하를 못 멈추는 것은 가드가
없는 것과 같다**(2026-08-03 의 800 Mbps 사고와 같은 구조).

로컬 kill 루프의 `pgrep -f "[m]..."` 가 **가드 자신을 매치**했다. bracket 패턴은 **원격 셸만**
보호한다 — 그 셸의 argv 에는 bracket 형태가 들어가지만, 가드 자신의 argv 에는 패턴이
평문(`watch iperf3 -c`)으로 들어 있다. 자기를 `kill -9` 하면 뒤따르는 원격 kill 이 실행되지
않고, **부하 생성기는 `c`(원격)에서 돈다.**

**A/B 실측** (표적을 로컬·c 양쪽에 띄우고 PID 로 판정):

| | 로컬 표적 | **c 표적(원격)** | guard 종료코드 |
|---|---|---|---|
| 조상 PID 제외 미적용 | dead | **alive — 살아남음** | **137** = 자기 SIGKILL |
| 조상 PID 제외 적용 | dead | **dead** | 2 = 정상 트립 |

조상 PID 제외를 추가해 수정했다. 상세: `CLAUDE.md` §규칙 0 · 커밋 `3f59a0b`.

> ⚠️ **검증 시 `pgrep -c` 로 생존을 세지 말 것.** 그 명령을 담은 **셸 자신**이 매치되어
> "살아 있다" 고 오판한다. 이번에 실제로 한 번 틀려서 정상 동작하는 kill 경로를 결함으로
> 진단했다. PID + `kill -0` 로 판정한다.
>
> 같은 자기매치 함정에 이 세션에서 **세 번** 걸렸다 — 가드 코드 자체, `pgrep -c` 검증,
> 그리고 가드 정지용 임시 `pkill`(제 셸이 죽어 exit 144). 스크립트 밖 임시 명령에서도
> bracket 패턴이 습관이 되어야 한다.

## 7. 절차 (재현)

```bash

$G watch "iperf3 -c" &

# 4. 리스너 (s) — 터널 IP 에 바인딩
ssh s "iperf3 -s -B 10.9.10.1 -p 5201 -D"

# 5. 부하 (c) — 목적지도 터널 IP
ssh c "iperf3 -c 10.9.10.1 -p 5201 -u -b 4M --bidir -t 60 -i 10"

$G sample

# 8. 정리 — bracket 패턴 필수
pkill -f '[m]f_gwguard.sh watch'; ssh s 'pkill -f "[i]perf3 -s"'
```

## 9. 계단 시험 — 실용 한계 재측정

`mf_ladder_udp.sh`, 단계당 45초, 가드 상시 가동. UDP 를 쓴 이유는 고정 레이트라 부하가 예측
가능하고 손실이 그대로 보이기 때문이다. TCP 는 스스로 레이트를 조절해 "어디서 무너지는가" 를
흐린다.

| 앱 각 방향 | c→s 실효 | s→c 실효 | c→s 손실 | s→c 손실 | c 전체 CPU | c 최고1코어 | OoO | 판정 |
|---|---|---|---|---|---|---|---|---|
| 4 | 4.00M | 4.00M | 0% | 0% | ~26% | — | 887 | ✅ |
| 10 | 9.99M | 9.99M | 0% | 0% | 43.0% | 48.0% | 2,128 | ✅ |
| 12 | 12.0M | 12.0M | 0.0018% | 0% | 46.0% | 69.7% | 2,465 | ✅ |
| 14 | 14.0M | 14.0M | 0% | 0% | 43.4% | 63.5% | 2,963 | ✅ |
| 16 | 16.0M | 16.0M | 0.0014% | 0.0055% | 45.8% | 67.5% | 3,268 | ✅ |
| 18 | 18.0M | 18.0M | 0% | 0.033% | 46.2% | 64.8% | 3,806 | ✅ |
| **22** | **22.0M** | **22.0M** | **0%** | **0.034%** | 47.5% | 66.8% | 4,652 | ✅ **한계** |
| 26 | 25.9M | 25.9M | 0.058% | 0.13% | 58.0% | 79.2% | 5,840 | ⚠️ 손실 |
| 30 | 29.8M | 29.7M | 0.31% | 0.79% | 63.3% | 79.1% | 9,187 | ⚠️ 손실 |

무릎점 전용 런(각 22 Mbps, 세 호스트 4회 샘플, `raw_knee_22M_4samples.txt`):

| | 전체 CPU | 최고 1코어 | 회선 |
|---|---|---|---|
| **c** (Atom N2600) | **56.9%** | **74.7%** | 118.3 Mbps (1 GbE 의 11.8%) |
| r (Xeon VM) | 19.2% | 29.3% | 238.2 |
| **s** (Xeon L5640 VM) | **12.6%** | 17.3% | 120.1 |

앱 22.0/22.0 Mbps, 손실 0.002% / 0.057%. 계단의 같은 단계가 c 47.5% 였는데 이 런은 56.9% 다 —
**1초 창 샘플의 창간 편차가 ±5\~9 포인트**임을 뜻한다. 단일 샘플로 판단하지 말 것.

### 9-가. 옛 8 Mbps 한계는 gw 바운드였다

기존 문서의 "실용 한계 앱 각 8 Mbps" 는 CPU 가 아니라 **gw 한계**였다. 산수가 맞는다:

```
gw 70 Mbps(방향당) ÷ 증폭 3.54(헤어핀 2회 계상 포함) ≈ 앱 각 방향 8 Mbps
```

gw 가 경로에서 빠지자 **각 방향 22 Mbps** 까지 손실 0.034% 이하로 나간다 — **2.75배**.
새 한계는 CPU 바운드이고, 34 단계에서 최고1코어 85.7% + 실효 미달 + 손실 14% 로 붕괴한다.
**단일 스레드 천장이 거기다.**

### 9-나. 병목은 `c` 단독이다

무릎점에서 c 56.9% / r 19.2% / s 12.6%. `r` 은 중간 홉이라 회선은 2배지만 raw 포워딩이라
CPU 는 싸고, `s` 는 하드웨어가 훨씬 빨라 여유가 많다. **한계를 올리려면 `c` 를 손대야 한다** —
인스턴스를 쪼개거나(단일 스레드 우회) 하드웨어를 바꾸거나.

### 9-다. ⚠️ 가드 임계가 느슨하다

계단 전체에서 **초과 3건 / 트립 0건**. 붕괴 단계(34)에서 **손실 14% 가 나는데도** 최고1코어
85.7% 가 임계 90% 에 못 미쳐 트립하지 않았다. **가드가 붕괴를 못 잡았다.**

최고1코어를 **80%** 로 내리면 26 단계(79.2%)부터 걸리기 시작해 손실이 0.1% 를 넘는 지점과
맞는다. `GW_CORE=80` 으로 조정하는 것을 권하되, 26·30 단계가 "동작하지만 손실 있음" 구간이라
운용 목표를 어디에 두느냐에 달렸다 — **미결정으로 남긴다.**

### 9-라. 재정렬이 레이트에 비례해 늘어난다

OoO 가 887(각 4) → 4,652(각 22) → 21,011(각 34). 경로 지연차 5 ms × pps 다. UDP 라 이번엔
무해했지만 **TCP 에서는 이것이 피해로 바뀐다**(재정렬 측정의 `지연차÷RTT` 결론). 이 한계값을
TCP goodput 으로 그대로 옮겨 쓸 수 없다 — 별도 TCP 런이 필요하다.

## 10. 용량 모델은 고배율에서 2.1배 과대다

| 앱 각 방향 | R (양방향) | 모델 예측 c CPU | 실측 | 오차 |
|---|---|---|---|---|
| 4 | 8 | 22% | ~26% | 모델이 약간 낙관 |
| **22** | **44** | **118%** (비용 4.71 논리CPU) | **56.9%** | **모델이 2.1배 과대** |

모델은 12 Mbps 한 점에서 **선형 외삽**했는데 실제 비용은 강하게 **sublinear** 다. 레이트가
오르면 ① FEC 그룹 크기 `g` 가 커져 패킷당 패리티 오버헤드가 줄고 ② `recvmmsg`/`sendmmsg`
32슬롯 배치가 훨씬 잘 채워진다.

제약 ②(개별 15.9 Mbps)·③(NIC 31.25 Mbps)도 실제와 맞지 않는다 — **R=44 를 깨끗하게 통과**했다.
**모델은 12 Mbps 근방에서만 유효하고 그 위에서는 과도하게 보수적이다.** `budget` 판정이
"✗ 초과" 를 내도 실제로는 도는 구간이 넓다는 뜻이므로, 재도출 전까지는 판정을 참고용으로만 쓴다.

## 11. `s` 가 `c` 와 같은 하드웨어라면 — 추정 약 57%

**하드웨어**

| | c | s |
|---|---|---|
| CPU | **Atom N2600** @1.60GHz (EIST 확인: 부하 시 1596 MHz) | **Xeon L5640** @2.27GHz (VM) |
| 논리코어 | 4 | 4 |
| 가속 | `ssse3` 뿐 | `ssse3 sse4_2 aes` |

**단일코어 성능비** (실측)

| 벤치마크 | c | s | 비율 |
|---|---|---|---|
| ChaCha20-Poly1305 1024B (WG 가 쓰는 것) | 99.1 MB/s | 427.3 MB/s | **4.31×** |
| 정수 루프 | 14.08 s | 2.48 s | 5.68× |

**환산**: `s` 실측 12.6% × 성능비

```
crypto 비율 4.31×  →  54.3%
혼합 추정   4.5×   →  56.7%     ← 최선 추정
정수 비율   5.68×  →  71.6%     (상한)
```

**최선 추정 약 57%** 로, `c` 실측 56.9% 와 거의 같다. 우연이 아니라 두 끝점이 하는 일이 대칭이기
때문이다 — 양방향 WG 암복호, obfs 인·디코드, dedup, 그리고 한쪽 FEC 인코드 / 다른 쪽 디코드.

**따라서 한계는 거의 안 움직인다.** 두 끝점이 함께 ~57% 가 되어 무릎점이 여전히 각 방향
22 Mbps 부근에 남는다. 다만 **약간 낮아질 요인**이 있다: `s` 는 FEC **디코드**를 하므로
손실이 커지면 RS 디코드가 인코드보다 비싸져 `s` 비용이 더 빨리 는다. 이번 측정은 손실
0.002\~0.057% 라 디코드 일이 거의 없었다.

**신뢰도 — 추정이다.** ① 성능비가 벤치마크 기반이고, syscall·메모리 바운드 구간은 ALU 성능만큼
스케일하지 않아 실제 배율은 4.31 보다 작을 수 있다(→ 예상치가 54% 아래) ② `s` 는 VM 이라
12.6% 에 virtio 오버헤드가 포함돼 있다(베어메탈이면 단일큐 실물 NIC 비용이 대신 붙어 대략
상쇄로 본다) ③ 확정하려면 Atom 급 장비에 서버를 올려 직접 재야 한다.
