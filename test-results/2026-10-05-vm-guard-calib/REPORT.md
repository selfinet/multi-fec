# VM 테스트망 가드 재보정 — 손실의 정체는 소켓 버퍼였다 (2026-10-05)

신규 테스트망(전부 Proxmox VM)에 WG·netem 을 올리고 부하 가드 임계를 VM 기준으로 다시 잡으려다,
**정상 부하에서 0.4~1% 손실**을 만났다. 원인은 CPU 가 아니라 **세 호스트 모두의 UDP 수신 버퍼**였고,
`rmem_max` 를 올리자 손실이 10~100분의 1로 줄었다. 가드 임계는 그 정상 분포로 정했다.

## 1. 구성

```
c .92 ── path[0] → r .88:443  (relay,   ens18) ──┐
      └─ path[1] → r .117:443 (relay-b, ens19) ──┴─► s .102:443
```

| | 값 |
|---|---|
| 호스트 | 3대 모두 Ubuntu 24.04 · **2 vCPU**(QEMU Virtual CPU) · 3.9 GB · NIC 큐 1개 |
| 바이너리 | v1.3.4 전 홉 |
| 옵션 | 서비스 클라이언트(dj17-m)와 동일 — duplicate · mode 1 · `-f 5:1,20:4` · t10 · mtu 1350 · `--sock-buf 4096` |
| WG | `wg-fec` 10.9.20.1(s) ↔ 10.9.20.2(c), MTU 1300, AllowedIPs 상대 /32 만 |
| netem | `c↔r` 양방향 · path[0] 25ms/5% · path[1] 30ms/2% (구 망과 동일 값) |
| 경로 분리 | 릴레이 VM 1대에 **DHCP IP 추가**(ens19). 호스트 장애는 분리되지 않는다 |

**서비스와 다른 점**: 릴레이 1단(서비스 2단) · 두 릴레이가 한 VM · `-k --upstream`(서비스 `--route`) ·
netem 손실이 실회선보다 클 수 있음. **용량·손실 수치를 서비스 SLA 로 옮기지 말 것.**

## 2. 하네스 — iperf3 를 쓸 수 없었다

iperf3 3.16 의 UDP 송신은 **레이트와 무관하게 1코어를 100% 먹는다**(`-b 5M` 에서 98%,
`--pacing-timer 10000` · `-l 1200` 무효). 2 vCPU 에서는 측정 대상의 절반이다 — 첫 계단
(`raw/lad1`)에서 5 Mbps 인데 c·s 최고1코어가 98~100% 로 읽혔다.

→ **`mfgen.c`** 를 만들었다. 1ms 절대시각 틱마다 몫만큼 보내고 자며, 페이로드 시퀀스로 수신측이
손실·중복·재정렬을 정확히 센다. CPU 는 top 상위에 나타나지 않는다.

| 파일 | 역할 |
|---|---|
| `mfgen.c` | 부하 생성기 + 시퀀스 계측 (`gcc -O2 -static`, 바이너리는 커밋하지 않음) |
| `hostsamp.sh` | 호스트 로컬 1초 샘플러 — 코어별 busy·softirq·steal·iface Mbps·multi-fec CPU. ssh 비용이 피측정계에 얹히지 않는다 |
| `run_load.sh` | 가드 기동·생존 확인 → 샘플러 → 단계별 mfgen 양방향. 트래픽은 WG 주소 사이만 |
| `analyze.py` | 스텝별 호스트 부하 분포 + 초 단위 손실 |
| `replay.py` | 기록된 1초 샘플을 후보 임계·연속 N회로 재생해 트립 여부 판정 |

## 3. 손실 — 버퍼를 키울 때마다 위치가 옮겨갔다

### 3-1. 버퍼 단계별 결과 (각 방향, 9분 지속, 전체 손실률)

| 버퍼 | 20 Mbps 상/하 | 25 Mbps 상/하 | 소켓 드롭 `UdpRcvbufErrors` (19분, c / r / s) |
|---|---|---|---|
| ① 기본값 (`soak`) | 0.448% / 0.558% | 0.429% / 1.021% | 미기록 (10 Mbps 45초에 **r 만 647**, c·s 0) |
| ② 릴레이만 확대 (`soak2`) | 0.346% / 0.388% | 0.646% / 0.916% | **43,466** / 1,395 / **42,863** |
| ③ **전 호스트 확대** (`soak3`) | **0.007% / 0%** | **0.036% / 0.043%** | **0** / 1,665 / 598 |

계단(45초, 각 방향):

| Mbps | ① `lad2` 상/하 | ② `lad3` | ③ `lad4` |
|---|---|---|---|
| 5 | 0 / 0 | 0.196 / 0 | **0 / 0** |
| 10 | 0.201 / 0.356 | 0.256 / 0.333 | **0 / 0** |
| 15 | 0.014 / 0.205 | 0.772 / 0.448 | **0 / 0** |
| 20 | 0.339 / 0.375 | 0.018 / 0.022 | **0 / 0** |
| 25 | 1.435 / 0.832 | 1.632 / 1.708 | **0.316 / 0.114** |

①에서 손실은 **한 초에 수백 개씩 몰려** 나왔고 상·하향이 같은 초에 겹쳤다(10M sec18, 20M sec29).
그 순간 릴레이의 1초 평균 CPU 는 50~65% 로 평범했다. 처음엔 VM 의 짧은 멈춤으로 추정했으나
③으로 **기각** — 버퍼만 바꿨는데 사라졌다.

### 3-2. 왜 잘려 있었나

| 소켓 | 요청 | 실제 (기본 커널) | 원인 |
|---|---|---|---|
| c·s mud (`--sock-buf 4096`) | 4 MB | **416 KB** | `rmem_max`=212992 에 잘림. 로그는 `sock-buf=4096 kB` 라고 찍는다 |
| c·s WG 쪽 소켓 | 1 MB (하드코딩, `common.cpp` `set_buf_size`) | 416 KB | 같음 |
| r 리슨 | 1 MB (하드코딩) | 416 KB | 같음 |
| r upstream (세션당) | **없음** | 208 KB | `rmem_default` 그대로 |

**relay 모드는 `--sock-buf` 를 적용하지 않는다** — `main.cpp` 의 처리가 mud 소켓 전용이고 relay 는
그보다 앞에서 분기한다. 옵션은 오류 없이 받아들여진다. 그래서 릴레이는 `rmem_default` 까지
올려야 upstream 소켓이 커진다.

### 3-3. 적용한 것

| 호스트 | 파일 | 값 |
|---|---|---|
| r .88 | `/etc/sysctl.d/90-multi-fec-relay.conf` | `rmem_max`·`wmem_max` 8 MB, `rmem_default`·`wmem_default` 4 MB |
| c .92 · s .102 | `/etc/sysctl.d/90-multi-fec.conf` | `rmem_max`·`wmem_max` 8 MB (기본값은 건드리지 않음) |

적용 후 실제: mud 8 MB · WG 쪽 2 MB · r 리슨 2 MB · r upstream 4 MB. 되돌리기는 파일 삭제 →
`sysctl --system` → 해당 multi-fec 서비스 재시작(파일 주석에도 적었다).

### 3-4. 대조 — 구 테스트망 릴레이

같은 기본 버퍼로 30주 운용한 구 `r`: `UdpRcvbufErrors 1,650 / UdpInDatagrams 2,239,400,374`
(**0.00007%**). 같은 설정인데 신규 VM 은 10 Mbps 에서 0.26% — 차이는 설정이 아니라 호스트가
버퍼를 비우는 속도(여유)에 있다. **버퍼는 원인이라기보다 충격 흡수재이고, 신규 VM 에는 그 여유가 없었다.**

## 4. 가드 VM 임계

`mf_gwguard.sh` 에 `GW_NET=new`(호스트·인터페이스·precheck 주소 프리셋, r 링크는 ens18+ens19 합)와
`vm` 프로파일을 추가했다.

| 지표 | ③ 정상 최대 (1초 로컬 샘플) | **임계** |
|---|---|---|
| c 전체 | 80.5% | **85** |
| r·s 전체 | 83.0% | **88** |
| 최고 1코어 | 92.9% | **95** |
| 연속 | — | **3회** |
| 링크 RX+TX | r 315.8 Mbps (25M) | 400 (무변경) |

재생 검증(`replay.py`) — 최대 연속 초과:

| 런 | c80/vm83/core92/s3 | **c85/vm88/core95/s3** | c88/vm90/core97/s5 |
|---|---|---|---|
| lad2 · lad3 · lad4 · soak2 · soak3 | 통과(0~2) | **통과(0~1)** | 통과(0~1) |
| soak (①) | 트립(5) | 트립(5) | 통과(4) |

①의 5연속은 **측정 중 내가 세 호스트에서 apt 자동 업데이트를 끄던 순간**(systemctl disable ·
sysv-install)이다 — multi-fec CPU 는 오히려 낮았다. 부하가 아닌 외부 작업이고, 측정 오염이다.

실가동 확인: 새 임계로 가드를 띄워 각 20 Mbps 90초 — 초과 0건, 손실 0%.

⚠️ **붕괴 쪽은 검증하지 못했다.** 릴레이가 c 의 약 2배를 나르므로 링크 400 Mbps 백스톱이 각
~30 Mbps 에서 먼저 걸린다(`lad2` 30M 에서 r 406 Mbps 로 트립). CPU 가 무너지는 구간까지 가 보지
못했고 1코어 여유가 +2.1p 로 좁다. 이 가드는 손실 탐지기가 아니다 — 손실은 수신측 계측으로 본다.

## 5. 서비스망 함의 (미확인)

- dj17-m 클라이언트도 `--sock-buf 4096` — 커널이 기본값이면 **실제 416 KB**, ①과 같은 상태다.
- 서비스 릴레이 4대는 `--sock-buf` 가 적용되지 않는 구조다.
- 다만 서비스 레이트(지사당 평균 1 Mbps)는 여기서 손실이 시작된 레이트(10 Mbps~)보다 훨씬 낮고,
  경로마다 릴레이 호스트가 달라 드롭이 경로 간 상관되지 않는다. **영향 여부는 각 호스트의
  `nstat -az UdpInDatagrams UdpRcvbufErrors` 증가분으로 판단할 것.**

## 6. 운영 변경 기록 (신규 테스트망)

- WG `wg-fec`(c·s), `mf-netem`(c·r) — enabled
- sysctl 3.3 표
- apt 자동 업데이트 비활성 3대: `apt-daily(-upgrade).timer`, `unattended-upgrades` disabled,
  `20auto-upgrades` → "0" (원본 `/root/20auto-upgrades.bak-2026-10-05`)

## 7. 하네스 함정 (이번에 걸린 것)

- **`setsid cmd &` 의 `$!` 는 가드가 아닐 수 있다** — 잡 컨트롤이 켜진 셸에서는 setsid 가 fork 후
  종료해 `kill $!` 가 헛돈다. 탐색용 가드 1개가 고아로 남았다(정리함). `run_load.sh` 안에서는 해당 없음.
- 측정 중 다른 호스트 작업은 3대 동시 스파이크를 만든다(4절).
- 수신측 mfgen 소켓도 `rmem_max` 에 잘려 ②까지 157건 자체 드롭이 있었다 — ③에서 해소.
