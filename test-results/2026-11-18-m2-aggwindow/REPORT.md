# aggregate 단일 터널 처리량 상한 재현 — J1900 2대 직결 (2026-11-18)

**질문**: NF01M(J1900) ↔ sv1 aggregate 터널이 회선(직접 130~256 Mbps)·CPU 여유가 있는데 57~67 Mbps 에 머물고
client 에 `mud_send EAGAIN`·`pending queue full` 이 찍혔다(2026-11-18 01:11~01:12 NF01M 로그). 같은 현상을 시험 장비에서 재현한다.

## 구성
- client `.92`(J1900 4C) ↔ server `.93`(J1900 4C), Ubuntu 24.04 / 6.8, **enp4s0 1G 직결**.
- 경로 2개 = 같은 링크 위 IP 쌍 2개: path0 172.31.10.x 편도 30 ms, path1 172.31.11.x 편도 54 ms
  (양쪽 egress prio + u32 dst 필터 + netem, limit 20000). ping RTT 60.3 / 108.2 ms — NF01 실측 owd 30/54 ms 에 맞춤.

- WG `rq-wg` MTU 1300, 10.89.0.2 ↔ .1, AllowedIPs 상대 /32(규칙2 위반 0). 모두 `/root/rq/`, 일반 프로세스(timeout 7200), 유닛·netplan·sysctl 무변경.

- **재현됨.** 링크(900 Mbps+)·CPU(스레드 ~55 %, 코어 65~71 % 유휴) 여유 상태에서 aggregate 터널이 상·하향 ~72 Mbps 에 묶이고,

## 손실 위치 (07:56~08:20, `run5.sh`·`run5b.sh`·`parse5.py`, 원자료 `raw5/` `raw6/`)

1.4.4 기본(aggregate) TCP 8연결 30 s. 런 앞뒤로 양쪽의 nstat·tc -s(prio/netem)·ip -s link(enp4s0, rq-wg)·`/proc/net/udp` 소켓별 drops·ethtool·wg 를 떠서 층별로 대조.
"터널 손실" = 보낸 쪽 rq-wg TX 패킷 − 받은 쪽 rq-wg RX 패킷.

| 경로 하나 하향 | 102 | 680 | server 세션 소켓 rcvbuf 681 | 682 | 0 |

- **유선·netem·NIC 손실은 0.** 모든 손실은 multi-fec 앞단 — WG 가 multi-fec 로 넘기는 소켓(rcvbuf 8 MB, 패킷당 truesize 2,304 B = 약 3,640 패킷)이 넘치거나 client pending 이 넘친다.
- 지연차가 없으면 **재전송 수 = 터널 손실 수**(경로 하나: 1,530 vs 1,529, 682 vs 680). 지연차 30/54 ms 하향은 손실 0 인데 재전송 216 — 그때는 **재정렬이 재전송을 만든다**.
- client WG 입력 소켓 대기열 5 ms 샘플(경로 하나, 상향 20 s, `raw6/qsamp.txt`): 대기열이 쌓여 있는 시간 비율(30~75 %)과 multi-fec 스레드 CPU(33~65 %)가 초 단위로 같이 움직인다 —
  **대기열이 있을 땐 스레드가 쉬지 않고 처리 중**이고, 비면 쉰다. 즉 평균 CPU 55 % 는 "여유"가 아니라 **"바쁜 시간 비율"** 이다.
  처리량 85 Mbps ÷ 바쁜 비율 ~0.64 ≈ **133 Mbps = 이 장비에서 multi-fec 한 스레드의 처리 상한**(UDP 고정 속도 시험의 수신 상한 133 Mbps 와 일치).
- 정정: 앞 절의 "CPU 포화가 아니다" 는 평균만 본 해석이었다. 순간적으로는 포화되고, TCP 가 그 앞 큰 대기열(최대 ~300 ms)을 채웠다가 넘쳐 한꺼번에 줄이는 구조라 평균 이용률이 60 % 안팎에 머문다.
- 따라서 aggregate 로 회선을 더해도 늘지 않는다 — 병목이 회선이 아니라 multi-fec 프로세스 하나다.
