## 판단

- **J1900 은 duplicate 각 방향 30 Mbps 를 손실 없이 처리한다** — multi-fec 이 코어 하나의 \~50%. 이전 추정(VM 대비 2배 느림 → \~15 Mbps)은 **과소**였다.
  aggregate 는 40 Mbps 에서도 손실 0.1%.
- **1.4.1 과 1.4.0 의 CPU 는 같다**(차이 ±3%p, 측정 변동 안).
- 다음 한계는 CPU 가 아니라 **100 Mbps NIC**: duplicate 는 한 방향 회선이 앱의 \~2.1배(30 Mbps 에 송 63 + 수 63)라 앱 \~45 Mbps 에서 NIC 가 찬다(추정, 미측정).
- 호스트 CPU(tot)는 같은 부하에서도 5\~45% 로 흔들린다 — NIC 큐 4개가 각각 CPU 하나에 고정(irqbalance 꺼짐)이라 흐름이 어느 큐로 가느냐에 따라
  그 CPU 의 수신 처리 부담이 달라진다(한 방향 진단: 같은 40 Mbps 수신이 s 5% · c 20%). 장비 차이가 아니다(사용자 확인: 동일 장비, 커널 완화 설정 동일).
- 이 시험은 netem 없는 직결이다 — 손실·지연이 있는 실회선에서는 FEC 복구·재정렬 비용이 더해진다. 처리 한계 자체(35\~45 Mbps)는 아직 안 찾았다.

- **duplicate: 35 Mbps 까지 손실 0.15% 이하, 40 에서 상향 0.6~0.9%, 45 에서 11%** — 1.4.0 과 1.4.1 같다.
  45 Mbps 의 붕괴는 CPU 가 아니라 **client 100 Mbps NIC 송신**(duplicate 는 앱 × FEC × 2경로) — multi-fec 은 코어의 55% 로 여유가 있다.
- **aggregate 1.4.1: 50 Mbps 까지 손실 0.05% 이하** — 회선을 절반만 써서 NIC 한계가 뒤로 밀린다. multi-fec 코어 54~62%.
- 하향 \~0.1% 는 netem 손실(5%/2%)을 FEC 가 다 덮지 못한 몫(전 단계 공통).
- **결론: J1900 지사는 실회선 조건에서도 duplicate 각 방향 \~35 Mbps, aggregate \~50 Mbps 까지 처리한다(100 Mbps NIC 기준). 먼저 막히는 것은 NIC 이고 CPU 는 절반 정도 여유.**
